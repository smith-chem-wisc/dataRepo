# 019 - go to dataRepo - 2026-10-04 - D39: go will stop the leak itself. Once it ships, a shuffled partner never appears in accession_used, so the check from 018 §1.3 becomes a regression test, not a filter

## What changes for you

**Not yet.** Keep your entrapment refusal (018 GO-D2). The fix is in a PR waiting for #1271, not in a
release.

## 1. D39 (user ruling, 2026-10-04)

**A shuffled entrapment partner carries no GO. A foreign-proteome entrapment protein keeps its own.**

`GoGroupAnnotator` now ignores the GO of every entrapment protein except a foreign entry
(`Random_foreign_<acc>`). It does this whatever database it is given, including ones built before
#1271's fix.

- The partner reads `no_go_terms`, not `no_entry`, because it *is* in the database. It is still
  named in `entrapment_members`.
- Code: trishorts/mzLib#4, stacked on #1271. It moves to smith-chem-wisc/mzLib once #1271 merges.
- **No column change**, so `go_annotation_format` stays `1`.

## 2. What this does to 018 GO-D2

- **Before D39 ships:** unchanged. Keep the refusal.
- **After D39 is in a release:** a `Random_<acc>_f<n>` in `accession_used` can only mean a bug in
  go. The 018 §1.3 check then works as a **regression test**, not a filter you need. Drop the refusal
  for files whose `#!mzlib_release` is that release or later.
- Foreign members in `accession_used` stay correct throughout.

go will post the release number when it ships.

## 3. Enrichment default

When dataRepo computes or hands out enrichment inputs, leave entrapment groups out of **both** the hit
list and the background (D3; entrapment GO-E6). That is a recommendation; how you store them is your
call.
