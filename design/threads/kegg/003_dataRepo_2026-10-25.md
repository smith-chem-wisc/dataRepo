## KEGG-D1 (answer): the schema check

**T1 `reactome_membership`: passes, with one added column.**
- The columns, statuses and grain meet R2, R5 and R6.
- **Add `taxon`** (NCBITaxon, from the entry's own `<organism>`).
  - **The measurement:** today no target database mixes organisms. In each of the 29 target database files, the
    identified non-contaminant proteins are all of one taxon. No dataset identifies proteins of two organisms. This
    reads the catalog's identified proteins, not the whole files.
  - **Why add it anyway:** your own `shuffled_entrapment` text expects foreign-proteome entrapment entries, which
    would make a database mixed. With `taxon` on the row, view rule 2 (the id's species must match) becomes a check
    on the row's own taxon, not on `run.json`.
- **The release-free key is right.** T1 reads only the search XML, so the Reactome release does not reach a T1 row,
  and an input that reaches no row is not hashed. Two things go with it:
  - **`run.json` records where the mapping came from:** the UniProt release of the XML, and your measured match to
    Reactome 96 as a note, not an input.
  - **The build shows drift.** It writes a `catalog_checks` row per database counting the `not_in_release` ids
    against the pinned T2. It is informational, never a failure. So drift is a number in the catalog, not only a
    NULL in a view.

**T2 / T3 (`reactome_pathways`, `reactome_hierarchy`): pass.**
- **The key is right:** one artefact per (`ReactomePathways.txt` sha256, `ReactomePathwaysRelation.txt` sha256).
- **One per catalog:** we refuse a build that mixes two, as we do for go.obo (R9).
- **`human_equivalent_id`'s "same number and same name" rule** goes in your definition word for word.
- **Disease needs no column.** The view flags it by ancestry, from the closure (KEGG-D2). Your definition names the
  top-level id it uses.

**T4 `kegg_gene_links`: no status rows needed.**
- R5 exists so that "we looked and found nothing" never looks like "we did not look".
- **For a link list, the artefact is the "we looked".** T4 is written over the whole database, so once it exists for
  a database, no row means that UniProt lists no KEGG id for the entry.
- **"Not looked"** is a database with no artefact. The view tells the two apart (`kegg_links: 'none'` against
  `'not_run'`), and the build counts the coverage as it does for go.
- Since T4 shares T1's artefact (change 1), the two can never disagree about whether a database was read.

**Overlay databases (new, from the measurement).** Here is what we found in the overlay files:

| file | entries | Reactome refs | GO refs |
|---|---:|---:|---:|
| `aging_isoforms_mouse.xml` | 56 | 0 | 18 |
| `aging_isoforms_tier3_compartment_mouse.xml` | 11 | 0 | 0 |
| `aging_isoforms_tier1-2_mouse_agingPTM-v3.xml` | 18 | 0 | 0 |

- Their entries are isoforms such as `O35426-2`, whose entry `O35426` is in the base proteome XML, a **different
  target database of the same dataset**.
- **So T1 on an overlay database gives mostly `no_reference` rows,** and that is the true state of that file. Your
  definition has to say what the group level does with them. We propose two rules.
  1. **A member takes the rows of its `annotated_as` entry (go's (c)) from any of its dataset's target databases,**
     never only its own file. Your isoform rule then applies unchanged. Our measurement above already did this, which
     is why overlay isoforms count.
  2. **An overlay entry's own `no_reference` row does not mean "in no pathway"** when its `annotated_as` entry has
     rows.
- **If one accession appears in two of a dataset's target databases with different rows,** the build writes a
  finding and takes the union. Say in the definition whether you would rather we refuse.

**go's (c), as amended.** Our go 028 asked that (c) hold one row per member accession (whose rows it takes), not
(group, member) pairs. The members come from the bundle's `protein_groups.protein_accessions`.
- Your view (`proteins` -> `dataset_databases` -> (c) -> T1 -> T2) works unchanged on that shape.
- Your KEGG-G1 (`sequence_accession` on (c)) is a property of the accession, so it fits the amended (c). We support
  it.

**The duplication across `_agingPTM` variants (KEGG-P3): accepted.**
- The join is on `dataset_databases.sha256`, so the key has to be the searched file's own sha256.
- About 0.5 MB per variant is not worth a second key.

## KEGG-D2 (answer): a materialised closure, once per release

- **Materialise it** (77,465 rows, ~0.33 MB) as a third table in the per-release artefact, written by your mzLib code.
  The closure is your output, as go's is GO's (our go 028).
- **Why not a recursive view:**
  - The SQL tool runs every agent's query, and a recursive CTE there is the costly shape.
  - With a stored closure, every view is an equality join, and the definition of "ancestor" stays in your code, not
    in our SQL.
- **The reader refuses a cycle** in `ReactomePathwaysRelation.txt` and a child with no pathway row in T2.
- **Keep T3 (the edges) beside it,** for "direct parent" questions.

## KEGG-D4 (answer): the same path as go

- **mzLib writes each table as a headed TSV** (#1497's shape, for standalone use).
- **Our engine calls your builder in-process and writes the TSV to a temp folder.** It then reads the TSV back
  through your mzLib reader to accept it, checking the header's hashes against the inputs.
- **The artefact stores Parquet and `run.json` only** (R4). No TSV is stored.
- **That is what our GO engine does today**, minus the stored copy, which our next release drops. Its reader is
  in-house only because mzLib has none for go's files; yours would be in mzLib.
- **Please don't hand us rows directly instead.** The TSV round trip is the acceptance test, and it means a file a
  standalone user writes is the same as what we ingest.
