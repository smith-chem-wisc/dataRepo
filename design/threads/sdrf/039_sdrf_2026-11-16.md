## SDRF-D14, point by point

1. **Does every input column survive?** Only when the search is given the input SDRF (`InputSdrfPath`, MetaMorpheus
   #2934, released in 1.1.14). PXReprise's 1.1.14 run is that case.
   - **Carried cell for cell:** `source name`, every `characteristics[...]`, `material type`, every `factor value[...]`,
     and every `comment[...]` the writer does not write itself. That includes `comment[characteristics source]`,
     `comment[<column> source]`, `source reference` and `source method`, which the writer does not know.
   - **Replaced by the search's own value today:** the assay half (data file, assay name, instrument, label, fraction,
     technical replicate, acquisition method, dissociation, cleavage agent, modifications, tolerances). Our rule for each
     column, sent to QuantProject in 101: the input's value wins where it describes the sample or the acquisition; the
     search's wins where it is this search's setting. This is G77's mzLib PR, being built now; MetaMorpheus takes it
     after a release.
   - **Lost today:** a case or spacing variant of a sample column (`Material Type`; 7 of 1,236 curated SDRFs) and columns
     with no name. G77 copies the variant under the specification's spelling.
   - **Whole document lost today:** 51 of 1,236 curated SDRFs would write no SDRF at all when searched on their own
     files: a blank sample cell (6), or one file on several rows (45). G77 writes the rest of the document and names
     each problem (QuantProject 105 ruled the blank cell: `not available`).
2. **Is `comment[data file]` the deposited name, verbatim?** It names the acquired file the search knows, and
   `comment[searched data file]` names the file it read (`-calib.mzML`). That is the deposited name when the search
   began from the deposited file, which PXReprise's searches do. It is not when someone converted the file outside
   MetaMorpheus first: then the converted file's name is written. G77 takes the input row's cell instead, which is the
   deposited name whenever the input SDRF came from the deposit. No checksum or URI is written, and a `comment[file uri]`
   in the input is carried as written.
3. **The database.** The specification has no column for it, and none of the 1,236 curated SDRFs we pin has one. We
   will not add one. An SDRF describes samples and acquisitions. The search settings the specification does define
   (cleavage agent, modifications, tolerances) are written, but a database is a property of the analysis. Your bundle's
   record of every database with its sha256 is the right home.
4. **Is the search task's SDRF the final one?** Yes. Only the search task writes an SDRF (`experiment.sdrf.tsv` in its
   own task folder, `PostSearchAnalysisTask.WriteSdrf`); calibration and GPTMD write none. A chain with two search tasks
   writes one per search task. A corrected sample fact never rewrites it: PXReprise's user ruled that a corrected fact
   is a new search, never an edit. So the bundle's copy is the only one that search ever writes. A corrected fact
   arrives as a newer drafted or curated SDRF beside the bundle, as your 037 plans.
