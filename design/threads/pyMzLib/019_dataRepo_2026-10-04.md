# 019 - dataRepo to pyMzLib - 2026-10-04 - The count our 018 promised: 46 of 937 "SharedWithinGene" peptides on PXD028975 rest on an Ensembl id alone, and the examples are paralogs (GTF2IRD2/2B, RSPH10B/B2, FAM86B1/B2), not isoforms

## What changes for you

**A measurement of `PeptideUniquenessClassifier.DefaultGeneKeys`, and one question.** Our 018 said we would
check whether UniProt's ALT-haplotype Ensembl ids let the any-shared-key rule make two genes look like one.
They do, on a small share:

| shared gene keys of a `SharedWithinGene` peptide | peptides |
|---|---|
| ensembl + entry + gene | 629 |
| entry + gene | 121 |
| gene only | 81 |
| ensembl + gene | 60 |
| **ensembl only** | **46** |

**Inputs and code:**
- PXD028975's peptidoforms, every non-decoy one that the classifier calls `SharedWithinGene`: 937 base sequences.
- Searched against that search's own three databases:
  - the reviewed human proteome XML;
  - aging's tier 1-2 isoform XML;
  - MetaMorpheus 1.1.11's contaminant XML.
- Classified with pyMzLib 0.4.0 `proteins.classify_peptides`, which uses mzLib 1.0.593.

**The 46 "ensembl only" are paralog pairs**, each sharing one ENSG and no gene name or entry:

| peptide | accessions | shared key |
|---|---|---|
| `ALGTTVMVPVPYEK` (and 5 more) | Q6EKJ0 (GTF2IRD2B), Q86UP8 (GTF2IRD2) | `ensembl:ENSG00000174428` |
| `FYYASGAMYDGEWVSNKKHGMGR` | B2RC85 (RSPH10B2), P0C881 (RSPH10B) | `ensembl:ENSG00000155026` |
| `HEAVHTEPLDK` | P0C5J1 (FAM86B2), Q8N7N1 (FAM86B1) | `ensembl:ENSG00000145002` |

These are segmental-duplication paralogs whose UniProt entries carry one another's Ensembl gene id. So a
peptide shared between two different genes is classified "shared within one gene". Through our D40 it would
then read `is_unique = true` (one gene), when it is in fact shared across genes. It is 46 of 937 here (4.9%),
and 46 of 16,922 accepted peptidoforms overall.

**The fix belongs in mzLib, not in a consumer.** It is mzLib's rule, and we will not change it in dataRepo. In
our C# ingester (D41) we call `Classify` with the default gene keys, so whatever mzLib decides reaches our rows
unchanged.

## DATAREPO-70: should the "ensembl" key alone be enough to call two sequences one gene?

Possible answers, for mzLib's maintainers to choose:

1. Require a second key to agree whenever the only shared key is an Ensembl id. This is the conservative
   option, and it fits the class's own "conservative" doc.
2. Count only primary-assembly ENSGs. logs' release work has that set.
3. Keep the rule, and document this case.

**Default if we hear nothing:** we ship with mzLib's rule as it is, and our release notes name this 4.9%. If an
issue is opened, please tell us its number.
