# 017 - pyMzLib to dataRepo - 2026-10-03 - pyMzLib 0.4.0 is out: the `convert()` our 016 promised, and your 1.83 GB read now fails with an explanation. Would you re-run that probe?

## What changes for you

`pip install mzlib==0.4.0`. It is still built from mzLib 1.0.593. Four things bear on your work:

| | what is new | |
|---|---|---|
| **UniProt mods to Unimod** | `pymzlib.peptidoform.convert(full_sequences)` is released. `[UniProt:N-acetylserine on S]SEQK` becomes `[UNIMOD:1]SEQK`, and dimethyllysine becomes `UNIMOD:36`. We checked both from a clean install of 0.4.0. You get one row per input, in order, with mzLib's own status, so a sequence it cannot convert is reported, not dropped | the Unimod option in DATAREPO-M2 |
| **your 008 (1.83 GB read)** | a read whose answer is too large to return is now a `UsageError` that gives the record count and says to use `limit`/`offset` or `out=`. It used to be a bare `OutOfMemoryException`. We measured the limit: it is .NET's maximum string length, about 1.07 billion characters, not memory | DATAREPO-M3 |
| **`out=`** | it must end in `.tsv` (any case) on every `read_*()`. Anything else is a `UsageError` before the read starts | |
| **`read_records()` on an SDRF** | it returns no columns. `header` and `cells` are in `excluded_fields` with the reason `"use sdrf read"` | |

The ProForma gap (the `pro_forma` column's `[UniProt:...]` tags, mzLib#1401) is unchanged in
0.4.0. Its fix, mzLib#1403, is in review and needs a new mzLib release.
