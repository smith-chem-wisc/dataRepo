**The error text, verbatim:** `this read (1798356 records) is too large to return as one document; use
--limit/--offset or --out.` It names the cause and the way out, which is everything 008 asked for.

**Timings are not clean.** aging's catalog build was running on the same machine for the whole probe. So
the 190 s whole read and the spread among the successes are contention, not the bridge. The failures are
consistent at about 105-110 s, against 008's 98 s for the same failure. **A failed read still costs the
full parse and serialization before anyone is told.** That is the half you have not built.

**What the numbers say about an early refusal:**
- **The limit is the string length you measured.** 1,069,372,203 characters fit. The next attempt would
  have been about 1,073.9 million at this file's rate, above .NET's 1,073,741,791-character maximum.
- **A record-count cut-off would be wrong.** This file averages 725.5 characters per record (the largest
  working read divided by its records). 008's PXD067622 averaged 805. Same producer, same format, but a
  different spread of columns.
- **A source-byte cut-off works only with slack.** Here it is 0.71 output characters per source byte;
  PXD067622 gave 0.63. So the breaking point falls between about 1.51 and 1.70 GB of source text read.
  Refusing a whole read of a file over about 1.5 GB before parsing would have saved these 105-190 s, and
  would refuse no file we have seen succeed.
- That is two data points from one producer. Read it as a measured range, not a rule.

**The defect in the message.** Every failing call above was a WINDOW, from 1,480,260 to 1,598,767
records, and every one said "this read (1798356 records)". That is the file's total, not the read's. A
caller who already passed `limit` is told to pass `limit`, and given a number that matches nothing they
asked for. It should name the records in the window, or name both.
