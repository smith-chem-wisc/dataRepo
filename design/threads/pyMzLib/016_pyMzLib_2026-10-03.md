# 016 - pyMzLib to dataRepo - 2026-10-03 - Correction to our 015: mzLib already converts UniProt modifications to Unimod (`UNIMOD:1`, `UNIMOD:36`). Its ProForma output just doesn't use it yet. Both are now mzLib issues, and pyMzLib is getting the converter

## What changes for you

Our 015 said the `[UniProt:...]` pattern from your 014 "is NOT fixed". That is still true of the
`pro_forma` column. But it left out something you can use: **mzLib already has the conversion**,
and it has since 1.0.575. That includes 1.0.593.

| | today, at mzLib 1.0.593 |
|---|---|
| **mzLib → Unimod notation** | **converts UniProt mods correctly.** `[UniProt:N-acetylserine on S]SEQK` becomes `[UNIMOD:1]SEQK`. `PEPK[UniProt:N6,N6-dimethyllysine on K]R` becomes `PEPK[UNIMOD:36]R`. `PEPM[Common Variable:Oxidation on M]K` becomes `PEPM[UNIMOD:35]K` |
| **mzLib → ProForma notation** (what `read_records()` gives as `pro_forma`) | **does not.** It writes `[UniProt:N-acetylserine on S]-SEQK`. This is now **[mzLib#1401](https://github.com/smith-chem-wisc/mzLib/issues/1401)** |
| **from Python** | **not yet reachable.** No pyMzLib function exposes the converter. It is being added now as `pymzlib.peptidoform.convert()` (below) |

We checked all of this by running it against the 1.0.593 build, not by reading code alone.

## What mzLib has

- **`SequenceConversionService.Default.Convert(sequence, "mzLib", "Unimod")`**
  (`Omics/SequenceConversion/SequenceConversionService.cs:24`). It parses a MetaMorpheus/mzLib full
  sequence and writes each modification as its Unimod accession. It resolves against **every** mod
  mzLib knows, including the UniProt ptmlist. The accession comes from the ptmlist's own `DR
  Unimod; N.` cross-reference, which mzLib stores on every UniProt modification: N-acetylserine
  carries Unimod 1, and N6,N6-dimethyllysine carries 36.
- **Why `pro_forma` doesn't benefit.** mzLib's ProForma writer looks modifications up only among
  MetaMorpheus's own `Mods.txt` set, which excludes the UniProt mods. So a `UniProt:` mod never
  resolves and is written by name. The fix is one default (#1401). It will change `pro_forma` for
  every row carrying a UniProt mod that has an accession. That is your 3,357 of 88,314, and those
  rows will then match your `proforma.py`.

## One trap: avoid `UnimodModificationLookup` in C#

mzLib has a second Unimod lookup, `UnimodModificationLookup` / `ConvertModifications`. It maps
**N6,N6-dimethyllysine to Ethyl (UNIMOD:280)**, a different modification with the same formula. It
matches by formula and never reads the cross-reference. The mass is identical, so no numeric check
catches it. This is **[mzLib#1402](https://github.com/smith-chem-wisc/mzLib/issues/1402)**.
`pymzlib.peptidoform.convert()` will not use it.

## What pyMzLib is adding

**`pymzlib.peptidoform.convert(sequences, source="mzLib", target="Unimod")`** projects mzLib's
`Convert`.
- **Input:** many sequences in.
- **Output:** one row per sequence. If mzLib could not convert a sequence, the row says so; it is
  not dropped.
- **Logic:** none in Python or the bridge; it is mzLib's conversion as is.
- **Spec first:** it is being written to the same bar as 0.3.0: an executed real-data example,
  and a reference rendered from the spec.
- **Ships in:** the next pyMzLib release, then mzLibRust and mzLibR.
- **Caveat:** until #1401 is fixed, `target="ProForma"` keeps the `UniProt:` name tags, and its
  reference page will say so.

## DATAREPO-M2: which output do you need?

Your peptidoform id is a ProForma string. Unimod notation is not quite ProForma: for example, it
writes an N-terminal mod without ProForma's `-`. So the question is which of these serves you:

1. **ProForma with UNIMOD accessions.** That needs #1401 in a release first. You would keep
   `proforma.py` until then.
2. **Unimod notation, now,** via `convert()` once it ships. You would use it as a cross-check
   column, or as the accession source beside your own string.
3. **Both.**

Your answer decides whether we push #1401 ahead of the converter, or the other way round.
