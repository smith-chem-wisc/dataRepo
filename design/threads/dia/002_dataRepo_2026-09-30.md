# 002 - dataRepo to dia - 2026-09-30 - DATAREPO-Q1: yes in principle, not on today's release. A DIA precursor needs a table of its own, and the files need a typed reader beside your writer. Eight things we need, most of which your draft already does

Thank you for writing before M7. Most of this is cheap to get right now and expensive later.

## What changes for you

1. **datarepo 0.32.0 cannot ingest these files.** Its ingester reads MetaMorpheus's DDA outputs only. We will add
   DIA; that is proposed, not built (our G82).
2. **A precursor will not go into our `psms` table.** A `psms` row requires a scan number and a USI built from it, and
   a DIA precursor has neither. A required column with no true value gets a false one, so precursors get a table
   of their own. That is a core schema change on our side; you do not need to do anything for it.
3. **Two asks (below): DATAREPO-65, a typed reader in mzLib next to your writer; DATAREPO-66, how contaminants are
   labelled.**

## What we need, against your draft

1. **Run key: the file name exactly as deposited, extension included.** Please make sure no step passes it through
   mzLib's `SpectrumMatchFromTsv` name handling. That deletes `.raw`, `.mzML`, `.mgf`, `.d` and the msalign
   extensions *anywhere* in the name, so PRIDE's `X.raw.thermo.raw` reads as `X.thermo`. It cost a deposit its
   ingest this week (aging 081, our 0.32.0).
2. **DATAREPO-65 (ask): a typed reader in mzLib, reachable from pyMzLib, for each of the three TSVs.** We do not
   parse producer formats ourselves when pyMzLib can; each in-house parser we still have is a listed gap with a
   request to delete it. If the reader ships in the same PR as the writer, the columns cannot drift apart.
3. **Labels.** Our `target_decoy` has `target`, `decoy` and `contaminant`, and no entrapment yet. `ET`/`ED` are fine
   as written; we will store them verbatim beside our column. **DATAREPO-66 (ask): how is a contaminant labelled?**
   Your four labels do not include one, and "no non-human proteins were identified" must not become true by default.
4. **q-values.** Say in each header which level it is and what it is computed over, which your names already mostly
   do. For `results.txt`'s `All target precursors with q-value <= 0.01: <N>`, say which of the four q-values it uses.
5. **Definitions.** The headline count and each quantity need a definition text that we can copy word for word, with
   a source commit, the way PXReprise publishes theirs (`DEFINITIONS.md` in their repo). Quantities should use
   QuantProject's `DEF-*` IDs where one fits. We store definitions; we never write them.
6. **Quantity: empty when not reported, never 0. Exactly right.** Please also state what a 0 would mean if one ever
   appears. We learned that a zero rule belongs to each definition, not to the column.
7. **Protein accessions.** Say whether the order of a `|`-joined list means anything; without that we treat it as
   unordered. If two `|`-joined columns are meant to align per protein, say so in the header. MetaMorpheus's are
   not, and we paid for assuming it twice.
8. **Retention.** `ApexRtMin` matches our convention (minutes, unit in the name), and keeping iRT in its own column is
   right. **Optional:** an apex MS2 scan number per precursor would let a row point at a real spectrum through a USI.

Modifications in MetaMorpheus notation, and the task TOML saved in the task folder, work as they do for DDA.
