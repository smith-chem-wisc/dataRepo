## Q5 (007): how DIA meets the ingest

- **The mode** is chosen as the isobaric one is: by the files the search wrote (`AllDiaPrecursors.tsv`), never by the
  manifest's `acquisition`. QuantProject's 101 asked the same; we answer them too.
- **Its required files** are `AllDiaPrecursors.tsv`, `AllDiaPeptides.tsv`, `AllDiaProteinGroups.tsv` and `results.txt`,
  as 0072 lists them.
- **Identifications come from `AllDiaPrecursors.tsv`,** into G82's precursor table. `psms` stays DDA's.
- **Quantities cite `DEF-DIA-*`** (QuantProject's DATA-DEFINITIONS v3.29). They are never read through the label-free path,
  never stored under `DEF-PEP-INT` or `DEF-PROT-INT`, and never pooled with DDA.

## Q2 (006): the precursor table, proposed

One row per (run, precursor), as `AllDiaPrecursors.tsv` writes it:

| column | from |
|---|---|
| `dataset_id`, `run_id` | the bundle; `File Name`, matched to the deposited run as every run is |
| `precursor_id` | the dataset, the ProForma peptidoform and the charge |
| `peptidoform_id` | joins `peptidoforms` (built from `AllDiaPeptides.tsv`) |
| `full_sequence`, `base_sequence` | `Full Sequence` (verbatim), `Base Sequence` |
| `precursor_charge`, `precursor_mz` | `Precursor Charge`, `Precursor MZ` |
| `protein_accessions` | `Protein Accession`, as a list |
| `label`, `target_decoy` | `Decoy/Contaminant/Target` verbatim (T, D, ET, ED, C), and our target/decoy/contaminant |
| `score` | `Score` |
| `q_value_run`, `q_value_global` | `QValue_Precursor_Run`, `QValue_Precursor_Global` |
| `library_irt`, `apex_irt`, `apex_rt_min` | `LibraryIrt`, `ApexIrt`, `ApexRtMin` |
| `apex_scan` | `ApexScanNumber` |
| `quantity_ms2`, `quantity_ms1`, `quantity_state` | `Precursor Quantity`, your MS1 column, `Quantity State`; a blank is no value, never 0 |

**No USI column, as proposed.** A USI names a spectrum that identifies a match. An apex scan is where the precursor's
traces peak, not a spectrum that alone identifies it. We would store `apex_scan` and build no USI, unless you and PSI's
USI rules say an apex-scan USI is right. Is that your reading too?

## Q3 (006): `confidence_rule` and `FeatureType`

- **`confidence_rule`:** since today (our D78, PXReprise's PXR-R81), a bundle's 1% rule is the filter the search itself
  applied, never one datarepo chooses. A DIA dataset gets a value of its own, defined by what your `DEFINITIONS.md` says
  the task applies: from your 006, run q ≤ 1% and global q ≤ 1% for precursors, and global q for peptides and protein
  groups. The DDA values are never reused, since DIA's results.txt line ("q-value <= 0.01") reads like 1.1.15's pooled
  q-value. We name the value when the mode is built.
- **`FeatureType`:** gains `precursor` with the precursor table.

## Q4 (006): your 004 folder, read now

`AllDiaPrecursors.tsv` in `Task1DiaLibrarySearchTask` (2026-10-06) holds 56,444 rows and 15 columns from one HeLa run.
Every row is typed as the columns above expect, and `ApexScanNumber` is on every row. Four things for the writer:
1. **Every row is a target at q ≤ 1%.** The file holds 56,444 rows, results.txt counts 56,444 target precursors at
   1%, and every label is `T`. Our tables keep everything the search wrote, decoys and rows above the threshold
   included, as DDA's `AllPSMs.psmtsv` does when the search writes decoys and high q-values. Then the 1% rule is
   applied in one place, a count can be reconciled, and an FDR can be checked. Can the DIA writer write all precursors
   (or have options to, as DDA's `WriteDecoys` and `WriteHighQValuePsms` do)?
2. **A comment line comes before the header:** `# contaminants: not assessed`. A TSV reader takes the first line as
   the header. If the fact matters, it belongs in results.txt or a column, so the table starts with its header.
3. **No MS1 quantity and no `Quantity State` column yet.** Both are planned (your 006, QuantProject's 067/068); we read
   this folder as written before them.
4. **One run only,** so `QValue_Precursor_Run` and `QValue_Precursor_Global` are equal on every row. Run and global
   cannot be told apart here.

**What would let us finish the dry read 0072 asks for:** one output folder from the current branch, after the writer
change, with all three `AllDia*` tables and results.txt, from a search of two or more runs. A small real deposit is
enough. Tell us its path.
