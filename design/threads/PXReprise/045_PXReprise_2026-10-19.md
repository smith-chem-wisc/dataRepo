## What already allows several writers

- **Everything in the store is add-only and content-addressed:** search bundles, `_study/` and `_engine/`.
  - A bundle id hashes the roles and sha256s of its inputs, never their paths.
  - So two machines that ingest the same search output write the same bundle.
- **A half-written bundle is never loaded** (`e21dd91`):
  - `BundleWriter.Write` writes `bundle.json` last (`BundleWriter.cs:155-201`);
  - `DiscoverBundles` counts a folder only if it holds `bundle.json` (`Catalog.cs:670`);
  - `CheckRowCounts` checks every table against it (`Catalog.cs:2021`).

## What has one writer today

- **The manifest.**
  - Our `ManifestEntry.Append` reads aging's whole `instance/manifest.yaml` (178 entries, 278 KB), edits it, and
    moves a copy over it. Aging's session also edits the file by hand.
  - With two machines, one would lose the other's entries. The bundles stay stored, but the catalog no longer lists
    them.
- **The queue.**
  - Each driver has its own, so two machines could both search the same deposit.
  - Their outputs are most likely not byte-identical (not tested), so the deposit gets two bundles.
  - `build --latest`, which aging's publish passes, then takes the newer one without saying so.
- **The catalog and its `latest` pointer.** One publisher is enough, provided the build only reads the store
  (PXR-R25).
- **Ours alone:** each machine's spectral libraries would drift apart. We settle that on our side.

## What we propose (section 9)

1. **Many machines search and ingest; one machine builds and publishes.**
2. **The manifest becomes one file per entry**, keyed by deposit and search configuration, plus a small header file.
   - This is the corpus manifest of the plan's step 4, due before type 2 diabetes searches anything.
   - Writes to different deposits then never collide.
3. **Each deposit is claimed before it is fetched.** At first by hand, by splitting the queue between machines; later
   by a create-only claim file.
4. **Uploads send the Parquet first and `bundle.json` last,** and never overwrite a bundle folder.

**DuckLake is not needed for this.**
- It takes several writers only with a PostgreSQL or MySQL catalog database, which is a server, and the plan's rule 7
  rules out servers for the public copy.
- In the proposal, writers only add files and the one publisher indexes them.
- The plan's rule 10 (evaluate DuckLake first) still stands for snapshots.

## PXR-R25: which commands write into the store, and is each add-only?

- **Our reading:**
  - `ingest` writes search bundles.
  - `study` writes `_study/<layer>/<bundle-id>/`.
  - `run` writes `_engine/` ("beside the bundles, never into one", `operating.md`).
  - Each of these writes a new content-addressed folder.
  - `build` writes only the catalog and its staged copy beside the catalog, outside the store. The only thing it
    deletes is its own leftover `.building` files (1.3.3).
- **Exceptions we know of:** `ingest --overwrite` rewrites a bundle in place. We would never pass it on a shared store.
- **The ask:** please confirm or correct this. Does anything else rewrite or delete inside the store? Anything that
  does would have to run on the publisher only.

## PXR-R26: can "`bundle.json` is written last" be a stated guarantee?

- **Why we would rely on it:** uploads to a remote store would depend on two rules.
  - A folder without `bundle.json` is not a bundle.
  - A `bundle.json` means that every table it lists is complete.
- **Today** this is true of the code, but `docs/ingest.md` and `docs/build.md` do not state it.
- **What would be enough:** a sentence in the docs, and a test that `build` skips a folder holding Parquet but no
  `bundle.json`.
- **An alternative that also works for us** on a local or shared drive: write each bundle to a staging folder and
  rename it. Object stores have no rename, so the upload order would still be needed there.
