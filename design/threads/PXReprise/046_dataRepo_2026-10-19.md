## PXR-R25: what writes into the store

| command | writes | how | deletes |
|---|---|---|---|
| `ingest` | `<store>/<accession>/<bundle id>/` | Parquet and `sources/` **in the final folder**, `bundle.json` last | nothing |
| `study` | `<store>/_study/<layer>/<bundle id>/` | the same way, `study.json` last | nothing |
| `run` | `<store>/_engine/<engine>/<artefact id>/` | in a staging folder `.<artefact id>.writing` beside it, then moved into place whole; refuses an artefact that exists | its own staging folder, and its scratch folders under the OS temp directory |
| `build` / `publish` | the catalog, and the site | outside the store, unless `--out` points into it | its own `.building`, `.building.wal` and `.building.owner` files beside the catalog, and only when their builder is gone (1.3.3) |

**The three corrections:**
- **ingest and study are not staged.** A killed ingest leaves a folder of Parquet with no `bundle.json`. Nothing
  loads it, and the next ingest of the same inputs writes into the same folder. On a shared store, two machines
  ingesting the same inputs at once would write the same files at the same time. That is safe only under your claim
  rule, so claim before ingesting, not only before fetching.
- **`study --overwrite` also rewrites in place,** like `ingest --overwrite`. Neither belongs on a shared store.
- **`build` writes into the store only if told to.** By default the catalog goes beside the store, never inside it.
  Never point `--out` inside the store.

Nothing else writes or deletes in the store: `query`, `mcp`, `site`, `catalog`, `manifest` and `doctor` only read.

## PXR-R24: the manifest as a folder

**Yes, with one change:** the header names the folder, so that a reader never infers it.

```
manifest.yaml            # manifest_version, instance, work_root, store, licence, credit, candidates,
                         # and entries: entries/   (relative to the header, or absolute)
entries/PXD057407.yaml   # one mapping, exactly as one item under `datasets:` reads today
```

- **One source per manifest.** A header with both `datasets:` and `entries:` is refused, so nobody merges two lists
  in their head.
- **Each entry file holds one mapping, and its name is its accession** (`<accession>.yaml`, then
  `<accession>.<configuration>.yaml` when your key lands). A name that disagrees with the entry is refused, naming the
  file.
- **The files are read in name order.** A repeated accession is refused, naming both files, and so is any other
  file in the folder.
- `datarepo manifest` checks the folder the same way.
- **Nothing that is hashed changes.** A bundle id hashes an entry's content fields, never the file it came from, so
  moving to a folder re-ids nothing.
- **Writers should write each entry to a temporary name and rename it into place.** Then a reader never sees half an
  entry, which also covers the half-written read we saw on 2026-10-04.
