### 2. Which deposits, and in what order

No engine reads another's artefact when it runs, so the order is not enforced. This is the order we would use:

1. **`logs.register_orthology`**, once. It takes no accession.
2. **`logs.resolve_genes`**, one run per species, over every re-ingested deposit whose bundle is that one organism.
   - The run refuses a whole call that holds a bundle of another organism, or of several (`LogsEngine.TargetDatabases`).
     So group the deposits by organism first. A deposit of two organisms gets no gene resolution.
   - Run it over all of each species' deposits. Do not replay each old artefact's `requested_for` list. On 11-13 that
     replay left two databases unresolved and cut PXD005035's gene names from 21,791 to 70, and the build passed.
3. **`go.categorize_terms`**, once. It takes no accession. A catalog serves exactly one: one go.obo and one map.
4. **`go.annotate_databases`** over every deposit, isobaric ones included. It writes one artefact per target database
   file, shared by every deposit that searched that file, and it skips contaminant panels.
5. **`go.resolve_members`** over the **label-free deposits only**.
   - An isobaric bundle has no `AllQuantifiedProteinGroups.tsv` (GO-D14). The run stops at the first one in the list,
     and the bundles before it in the list are already written.

Engine artefact ids hash the schema version. So in the live store every 1.0.0 run writes a new artefact beside the
1.4.x one, and none answers "already exists" from a 0.0.16 artefact. Each build skips the other schema's artefacts and
names them in its `engine-coverage` checks.

**`protein_localizations`, `organelle_term_categories`, `annotation_sources` and `go_group_status` come from no engine.**
- From catalog format 17, `build` derives them from go's three artefacts and each bundle's `protein_groups`
  (`CatalogGo.cs`; `docs/data/build.md`, "Cross-dataset tables").
- A search gets GO only when it has its `go.resolve_members` artefact and every target file it read has its
  `go.annotate_databases` artefact.
- Otherwise the tables are typed and empty for that search, and the `engine-coverage` checks name what is missing. Those
  checks always pass.

**For aging's publish:**
- On 1.0.0, a probe for `go.annotate_groups` finds nothing, and `datarepo run go.annotate_groups` refuses (it is
  retired).
- If the publish skips GO, the front-page summary reads two empty tables and no error is raised.
- So the publish should look for `go.categorize_terms` and run the three engines above.

### 2. Re-ingesting into the live store while it is half done

**Re-ingest into the live store, not a fresh one.** But pause two things for the window.

**Safe for what aging serves:**
- The serving catalog's views name each bundle's Parquet by its full path. For example, `protein_groups` reads
  `F:/aging_data/repo/store/PXD036557/0955c951b61e80ba/protein_groups.parquet`.
- A new bundle written beside the old one is invisible to it.
- Nothing in 1.0.0 rewrites a store-level file. The store holds no top-level files today. Each command writes only a new
  folder:

| command | writes |
|---|---|
| ingest | `<PXD>/<bundle id>/` |
| engines | `_engine/<engine>/<id>/` |
| `datarepo study` | `_study/aging/<id>/` |
| `datarepo pride` | `_companion/pride/` (1.4.5 never reads it) |

**Not safe for 1.4.5 builds:**
- 1.4.5's `publish` uses the same newest-bundle rule (`CatalogCommands.cs:250` at `v1.4.5`). Its build refuses a 0.0.17
  bundle ("was written against schema 0.0.17, and this build writes schema 0.0.16").
- So from the first 0.0.17 bundle until the swap, every 1.4.5 publish by aging fails. The refusal comes before anything
  is written, so `latest.json` stays on `7ecfc9763064b181` and serving goes on.
- **Pause aging's publishes for the window.**

**Not safe for 1.4.5 ingests:**
- A 1.4.5 ingest during the window writes a 0.0.16 bundle that is newer than that deposit's 0.0.17 one. 1.0.0's newest
  rule would then pick it and refuse.
- **Pause the batch's ingests too,** until both pins move.

**A fresh store swapped in is worse:**
- Renaming the folder breaks the catalog that is serving, because its views name `F:/aging_data/repo/store/...` paths.
- Keeping old and new bundles side by side is what makes your per-bundle comparison possible.
- It also makes rollback one step: point `latest.json` back at `7ecfc9763064b181`. That works while the old bundles are
  kept, and deleting them is the user's decision.

### 3. Freezing 0.0.17

**In the first PR that changes the working schema, whoever writes it.**
- `FrozenSchemaTests.TheWorkingSchemaIsNotAReleasedVersion` says "bump it before changing it, or freeze it here when it
  is released". So that PR moves `datarepo.yaml` to 0.0.18 and copies 0.0.17's core and study files, as they are at the
  `v1.0.0` tag, into `releases/0.0.17/` with their `SHA256SUMS`. It also adds 0.0.17 to `Released` and a row to the
  README table (study layer 0.7.0).
- The schema is ours, so we expect to write that PR. If yours changes the schema first, do it there.
- **Don't bump the version on its own:** a bundle id hashes the schema version. A bump with no change would give every
  bundle a new id at the next release while every row stayed the same.
