  Which release would carry it, and does the change move any existing bundle id?
- Until then, PXD011740 stays out of aging's store. Its search is kept on disk (2.2 GB). When your release is out we
  re-ingest it; it needs no new search.

## What happened

- **The deposit:** PXD011740 (aging). Half its runs are NEM-capped, half carbamidomethyl. Aging chose to search all four
  cysteine caps as variable mods through a curated SDRF (PXR-A103 option 3).
- **The search was fine:** 2026-10-14 15:28 UTC, 12 files, 89,023 PSMs, ID rate 35.4%. The QC payload validates.
- **datarepo 1.3.2 refused the ingest** at 16:06 UTC, and again at each driver start since:

  > modification name 'NEM:2H(5) on C' (from full sequence 'AEGSDVANAVLDGADC[Unimod:NEM:2H(5) on C]IMLSGETAK')
  > contains ':', which is the ptm_site_id separator. The mod token did not parse, so the name is not trustworthy as a
  > site key; fix the token's parsing rather than storing this row.

## Why the guard's premise does not hold here

- **The token did parse.** MetaMorpheus writes `[<type>:<name> on <residue>]`. Here the type is `Unimod` and the name
  is `NEM:2H(5)`, Unimod's own name for D5 N-ethylmaleimide (UNIMOD:776).
- **Colons are the rule for isotope labels in Unimod**, for example:
  - `Dimethyl:2H(4)` (UNIMOD:199);
  - `Label:13C(6)` (188);
  - `Label:13C(6)15N(2)` (259);
  - `Label:13C(6)15N(4)` (267).
- **They will become routine.** The user wants a dimethyl profile (QuantProject 055, PXR-Q6), and every labelled
  search will name these mods.
- **The guard is still worth keeping** for tokens that really did not parse. It just needs to tell those apart from a
  valid name that holds `:`. One way is to escape the separator inside the key; another is to split on a separator no
  Unimod name uses. The choice is yours.
