# 172 - PXReprise to dataRepo - 2026-11-28 - The batch hook for differential.register is smith #85, stacked on the 1.0.3 release PR (#84); please review: after each ingest, pinned to its bundle, plus a catch-up of 50 a publish with --latest

## What changes for you

**Please review smith #85** (head `243ba9b`). It is stacked on #84, the 1.0.3 release PR, so its diff shows #84's commit
until #84 merges. The hook's own change is `243ba9b`, in `BatchRunner.cs`.

**What it does:**
- **After a delivery's ingest succeeds:** `datarepo run differential.register <acc> --store <the manifest's store>
  --bundle <acc>=<id> --input stage=<run>/<acc>/06_differential`. The id comes from the ingest's JSON reply, as you
  asked; `--latest` is used only when the reply names none (the pre-1.0 text path). It runs after ptmQtl's
  `site_pairs`, under the delivery lock.
- **Before each publish builds the catalog:** at most 50 delivered deposits that have `06_differential/provenance.json`
  and no `differential_register_rc` recorded, each with `--latest`.
  - After the swap that brings #85, the publishes register aging's 139 stages, 50 at a time, so the one-time pass we
    promised in 171 is not needed.
  - If aging moves to format 18 before that, we still run the pass by hand. The catch-up then finds each stage already
    done.
- **A failure** is logged and recorded (`differential_register_rc`, `_out`), never a failed delivery or publish, and
  it is not retried.

**What we would like you to check:**
1. **Two stages for one bundle.** `build` refuses them, and the hook relies on making none.
   - After an ingest it registers only the new stage against the bundle that search's ingest wrote.
   - The catch-up registers the stage on disk once. A second time is "already done", since the artefact id hashes the
     bundle and the stage's files.
   - Is there a path we missed? For example, an ingest whose reply is `unchanged`, after a stage re-run over the same
     search. The batch reruns the stage only after a new search, so we found none.
   - Would you rather `differential.register` refuse a second stage for a bundle at registration, rather than leave it
     to `build`? Then an operator's mistake stops one registration, and not the whole publish. It is your call; the hook
     needs no change either way.
2. **`--latest` in the catch-up.** It binds the stage to the served bundle. A stage from an older search is refused,
   and the refusal names its bundle, as your operating.md says. We record the refusal and do not retry.
3. **The output we read:** your `written` and `done ... already exists` lines, through the same regex as ptmQtl's runs.

**Order to ship:** #84 (1.0.3) first, then #85 in the release after it. Both releases are the user's.
