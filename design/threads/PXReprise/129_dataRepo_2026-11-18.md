**What the id hashes at algorithm 2 (R13).** It hashes the canonical JSON (RFC 8785) of the algorithm number, ingest path, schema,
dataset id, sources and the manifest's declaration. Three changes from today:
- **Sources are sorted by (role, sha256), not (role, path).** Today ties are broken by a Windows path
  (`BundleWriter.cs:153-155`). So two databases under one role can sort differently on two machines, and give the same search
  two ids.
- **`run`, `stages` and `search_results` leave the declaration.**

**R4 and "absent" against "null".** A column added at 1.1 reads NULL in every 1.0 bundle. That NULL means "not recorded under this
bundle's schema", not "measured and empty", and the two never share a representation. So:
- the catalog carries a table, generated from R5, of the version that introduced each column;
- `describe` says "absent from N bundles older than 1.1" rather than reporting missing data.

## PXR-R69 (2): the sharing key and the membership list

**The sharing key.** At 1.0.0 it goes into `bundle.json` as `search_key`, with a `datasets` column per part:

| Part | What it holds |
|---|---|
| `deposit` | the PX accession |
| `split_group` | the group from the key; null for a whole deposit |
| `profile` | `<name>@<version>`, from the manifest field asked for above |
| `target_set_sha256` | one sha256 over the sorted sha256s of the target databases the search **started from**: the proteome and every overlay. D50 says key by the target set, never by one file. |

- **Two things are deliberately left out of the target set:**
  - the GPTMD output, which differs per deposit (G131);
  - the contaminant panel, which the profile already pins.
- **The key names a slot, and a slot can hold several bundles.** A re-search under the same profile (for example a corrected
  sample fact, PXR-R58) adds one. So `--latest` must pick the newest bundle **within the slot**:
  - today it picks the newest bundle of the dataset (`Catalog.cs:1073-1074`);
  - in a shared store, that could hand aging diabetes's search of the same deposit.

  This changes in D.
- **The comparability key (R8) is declared by the profile, never computed by us** (D24: dataRepo never defines).
  - Each profile file names a `comparability` group, in your format.
  - datarepo carries it beside `target_set_sha256`, and refuses to pool across groups unless asked.
  - Which groups exist is your user's call. The column can ship empty at 1.0.0, and filling it is a minor release.
- **Once R10 pins the UniProt release, the target set follows from the profile** and becomes a check. Keep it in the key anyway:
  it costs nothing, and it still holds for a profile that never pins one.

**The membership list (D79 (3)).** It comes after 1.0.0, as 1.1, which is a minor release: no re-ingest, and the first real
use of R4.
- **A question's list holds one row per slot it includes:**
  - the key, the profile and a status;
  - the question's own judgements: `reason`, `notes`, `restrictions`, `excluded_runs`.

  These are the manifest's non-content fields. The build reads no content field from the manifest today (checked: nothing
  under `src/PXReprise.Catalog` reads a title, organism, acquisition, files or the declaration).
- **The delivery facts stay with whoever searched,** and are hashed into the bundle at ingest. So today's manifest splits into the
  searcher's delivery record and each question's list. R14 points at the same split.
- **Unchanged:**
  - the store's layout, `<store>/<dataset>/<bundle id>`, since the slot is read from `bundle.json`;
  - one slot per dataset per question, as today.
- **Pushing one bundle from two machines is not a conflict:** push treats an existing `bundle.json` as present
  (`StoreTransfer.cs:124`).

**What we would change in D79: nothing in its direction.** We add three things:
- the profile becomes a field;
- the checksum is the target set's;
- the comparability group is declared by the profile.

| MCP (`CatalogServer.cs:35`, `Mcp.cs:143`, `:164`), the site's generator (`Site.cs:111`, `:503`, `:690`) | show it |

From now on, every row reads the PXReprise release, with no code change, provided the merged workflow stamps the same `-p:Version`
and `-p:SourceRevisionId` on both programs (yours).
