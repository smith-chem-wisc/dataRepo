# 015 - dataRepo to PXReprise - 2026-10-05 - Pin datarepo 1.1.0, not 1.0.0: it reads your four QC keys, and it is the release aging re-ingests on

## What changes for you

1. **datarepo 1.1.0 is published:** https://github.com/smith-chem-wisc/dataRepo/releases/tag/v1.1.0 (tag on
   `8779917`).
   - **Pin this, not 1.0.0:** aging re-ingests on 1.1.0 (our aging 086 and 090). It moves the schema to 0.0.15, so
     a bundle written by 1.0.0 is refused by a 1.1.0 catalog.
   - The archive names follow 014's pattern with the new version: `datarepo-1.1.0-win-x64.zip`, and
     `datarepo-1.1.0-<linux-x64|osx-arm64|osx-x64>.tar.gz`. Each unpacks to `datarepo/`.
   - `--version` prints `datarepo 1.1.0`, and `doctor`'s first line says the same with `schema 0.0.15`.
2. **Your DATAREPO-72 keys are read** (our G87). Each run's entry in `qc_report.json` maps to:

   | your key | our column |
   |---|---|
   | `start_time` with no zone (every RAW header) | `runs.acquisition_start_local`, VERBATIM, marked as the instrument's local clock, zone unknown; never shifted, never put in the UTC column |
   | `start_time` with `Z` or an offset | `runs.acquisition_datetime`, converted to UTC |
   | `instrument_model` | `runs.instrument_model`, with `instrument_model_source = qc_report`; without it, the SDRF's model, with source `sdrf` |
   | `instrument_model_accession` | `runs.instrument_model_accession`, always from the same source as the model, never paired across sources |
   | `instrument_serial` | `runs.instrument_serial` |

   - A missing key is NULL, as you defined it.
   - **A `start_time` that is not ISO 8601 refuses the ingest,** rather than being stored as a time. That is
     `yyyy-MM-ddTHH:mm:ss`, an optional fraction, and `Z` or an offset only when the reader gave a zone. Your
     examples in 013 all pass.
3. **The switch order is unchanged** (011, 014, aging 087): aging re-ingests into a new store, and you drain only
   for the final catch-up. aging coordinates the batch steps with you directly.
