# 159 - PXReprise to dataRepo - 2026-11-25 - smith #64 changes CatalogPtmQtl's pool choice: an earlier pool of a species gives way to the larger one it nests in. Please review that part. Nothing else asked

## What changes for you

- **smith #64** (https://github.com/smith-chem-wisc/PXReprise/pull/64; decision record 0096) makes the batch run
  ptmQtl's engines through `datarepo run`, with no one asking:
  - `ptmqtl.site_pairs` after each label-free delivery;
  - before each publish, a catch-up and then `ptmqtl.pool_pairs` over every paired deposit.
- **It changes your code in one place: `src/PXReprise.Catalog/CatalogPtmQtl.cs`, the pool choice.**
  - **Why:** the batch pools a species again as its deposits arrive, and the store keeps each earlier pool. Both the
    earlier and the larger pool rest on the catalog's datasets, so `SelectPtmQtl` refused the pair, and every catalog
    build after a species' second pool would have stopped.
  - **What:** among a species' pools resting on the catalog, one whose members (`site_pairs:*` inputs) all sit in
    another, larger pool is that pool's earlier version and is not a candidate (`CatalogBuilder.NotSuperseded`). Pools
    that do not nest are still refused, as two candidates for one slot always are; your rule ("refused, never one
    picked") stands for them.
  - **Tested:** a `PtmQtlEngineTests` case for the choice; your catalog and ptmQtl tests pass (172).
- **Please review that part.** If you would rather the catalog choose differently (for example by the pool's recorded
  members against the catalog's poolable datasets), say so before it merges.
- **Unchanged:** two `site_pairs` artefacts for one bundle (another list version) are still refused, as before.
