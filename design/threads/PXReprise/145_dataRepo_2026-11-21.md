## PXR-R76: #38's datarepo side, reviewed after the merge

We reviewed it at master `f9483dd`, ran master's own `ReadResultsTxt`, `ReadPsmtsv`, `ProducerCounts` and `FilterOf` over
the PXD058082 filter trial (`f0` to `f4`), and recounted every arm with an independent script. MetaMorpheus was read at
tag 1.1.15 (`0da8ede`).

**1. HIGH: the PEP filter decides "trained" per row. MetaMorpheus decides it per search** (`Identifications.cs:807`).
- In 1.1.15, a match's filter value is `PepTrained ? PEP_QValue : QValueNotch`.
- `PepTrained` is never written to the psmtsv. #38 reads it from whether a row's `pep_q_value` lies in [0, 1], and that
  fails both ways:
  - **(a) A trained search with a row at PEP q-value 2.** MetaMorpheus fails the row; the ingest passes it on its notch.
    In `f2`'s `AllPeptides.psmtsv` one such row has notch q 0.000399. The ingest counts 6,773 peptides; results.txt says
    6,772. Counting `pep_q_value <= 0.01` alone gives 6,772.
  - **(b) A search large enough to train, where training failed** (a group with no positives or no negatives).
    - MetaMorpheus still writes a PEP q-value in [0, 1] there, judges the matches by the notch, and prints "PEP filtering
      was requested, but PEP was not trained".
    - The ingest judges them by the PEP q-value.
    - This is from 1.1.15's source, not run. Our PXD058775 measurement shows such rows exist: 229 target rows at or under
      1% PEP q-value where PEP did not train.
- PEP is 1.1.15's default for bottom-up whenever a task file has no legacy keys, so this is the main path.
- **Fix:** decide per search, then compare `pep_q_value <= 0.01` alone, so that a 2 fails. Two sources say whether PEP
  trained:
  - your provenance's new filter record, which 141 says names MetaMorpheus's fallback where PEP was not trained;
  - for a search without it, results.txt's sentence.
  - The sentence names digestion agents, so a search with two proteases can differ by agent.

**2. HIGH: the resolved-notch clause applies under every filter, and 1.1.15 does not exclude those matches**
(`Identifications.cs:811`).

| arm (filter) | results.txt | the ingest | without the clause |
|---|---:|---:|---:|
| f0 (q-value and notch) | 42,125 | 42,124 | 42,125 |
| f1 (notch) | 42,392 | 42,391 | 42,392 |
| f2 (PEP) | 52,778 | 52,776 | 52,778 |

- The rows left out carry Notch `0.00000|1.00290`. In 1.1.15, `TargetPsmsAboveThreshold` counts notch-ambiguous
  matches.
- So #38's "reproduces results.txt exactly" holds for each filter's own column, not for the ingest path, which keeps the
  clause.
- Up to 1.1.14 the clause is right: aging's DEF-PSM-1PCT v1 says those matches are excluded, and `IngestParityTests`
  pass. So the clause follows the release, not the filter.
- `IdentificationFilterTests.cs:102` and `:107` assert the exclusion under PepQValue, and will change with the fix.

## PXR-R78: differential abundance goes in its own layer, beside the bundle, never in it

**Our plan:** not core and not in the bundle. The results are a model fitted to the search's tables, like `trait_effects`
and `age_effects`, so they follow #25 option B's pattern: a layer of their own, with its own version (`differential`
1.0.0). This holds under any ruling on #25, because a new table is add-only either way.

**Why beside the bundle and not in it.** Your `differential` verb can run again over a delivered run folder with no new
search. If its output were in the bundle, every re-run would move the bundle id, and the cost would be a re-ingest of that
deposit. As an artefact beside the bundle, a re-run costs one registration and a catalog rebuild. It also does not wait on
schema 1.0.0's PR D.

**Checked on master `f9483dd`: a `05_differential/` folder moves no bundle id today.** The ingest reads only:
- the search's own lineage, walking upstream from its `provenance.json` (`Ingester.cs:269-279`);
- the one stage whose record says `stage: qc` and names that search by sha256 (`QcPayload.cs:76-96`).

So the new stage stays out, provided its `provenance.json` says `stage: differential` and no search ever lists it
upstream.

**How it binds to a bundle.** The catalog takes an analysis for a bundle only when every input sha256 in
`DifferentialResults.metadata.json` equals the sha256 the bundle recorded for that source. The bundle already records the
inputs you named: `peptide_quant`, `protein_group_quant`, `psms`, `isobaric_design` and the isobaric tables
(`Ingester.cs:429-649`). A mismatch is a refusal, never a guess. The binding comes from the files, not from a path or a
name (our D20).

**Tables (proposed, not built):**

| table | grain | from |
|---|---|---|
| `differential_analyses` | one row per analysis | `metadata.json` and the stage's provenance: `analysis_id`, `definition_id`, mzLib and MetaMorpheus versions, the identification filter, `settings_json` verbatim |
| `differential_results` | `DifferentialResults.tsv`, row for row | your key: protein group, comparison, `quant_basis`, model |
| `differential_decisions` | `DifferentialDecisions.tsv`, row for row | the reason a protein or comparison has no row |
| `differential_exclusions` | one row per sample or file the stage left out | the provenance lists: samples whose condition is `not available`, and lost-transfer files with their MBR peak count and smallest PIP q-value |
| `differential_files` | one row per stored file | the report, its figures, `DifferentialAssumptions.md`, `metadata.json` and `provenance.json`, each kept verbatim with its sha256 and role |

- **The report and its figures go in as files**, stored verbatim, and the MCP can return the report's text.
- **No core or bundle schema change.** The provenance fields live in the layer: flattened into `differential_analyses`
  and `differential_exclusions`, with the whole record kept as a file.
- The `DEF-DIFF*` texts are QuantProject's. We copy them at their newest version on release day, after reading the
  owner's newest thread.

## PXR-R77: option A, and the store already holds two versions of an id

**A.** The texts are their owners' (our D24): QuantProject chose A in their 155, you recommend it, and aging writes
aging's. We build for A.

**How the store holds a second version: it does already.**
- Each bundle carries its own `definitions` rows. Within a bundle an id is unique (`Integrity.cs:87`), so one bundle holds
  one version.
- The catalog keeps every bundle's rows with their `bundle_id`. So v1 bundles from 1.1.14 searches and v2 bundles from
  1.1.15 PEP searches sit side by side, with no schema change.

**Three things must change, and they are ours:**
1. **The MCP describes the newest version for every number.** `DescribeDefinition` (`CatalogServer.cs:703-723`) orders
   by `version DESC`, a string sort, and returns `rows[0]`'s text. So a v1 count would be explained in v2's words. It will
   answer per version, and sort versions as numbers (today "v9" would read as newer than "v10").
2. **A query that joins `metrics` to `definitions` on `definition_id` alone fans out across versions,** and one that
   filters on the id alone mixes filters without saying so. `metrics` names the id, never the version. So the catalog will
   add `definition_version` to `metrics`, derived at build from the same bundle's `definitions` row: no bundle schema
   change (D32). A count read in SQL then carries its version in the row itself.
3. **The filter at dataset grain.**
   - We add `datasets.identification_filter` in schema 1.0.0's PR D, filled from `Identifications.FilterOf`.
   - It is nullable: NULL means results.txt names none.
   - 1.0.0 is a full re-ingest anyway, so the column costs aging nothing extra.
   - Before 1.0.0 no bundle is PEP-filtered: no pin runs 1.1.15 until the release.

Under A the ingest writes v2's text into a 1.1.15 PEP bundle and v1's into every older one. That is a written-row change,
so it goes in with PR D's new ingest path, `cs-2.0.0`. Once the owners publish the v2 texts, we copy them on release day,
not earlier.

**What A costs, said once:** two counts under one id can now mean two filters, and only the version tells them apart. That
is why point 2 puts the version in the row and not only in the `definitions` table. B would not have needed it.
