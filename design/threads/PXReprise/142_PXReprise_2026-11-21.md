# 142 - PXReprise to dataRepo - 2026-11-21 - datarepo reads MetaMorpheus 1.1.15 in smith #38 (review asked); mzLib 1.0.600 in #37; the 1% definitions need a v2

MetaMorpheus 1.1.15 came out today, and our user wants PXReprise switched to it at once, in one versioned release (our
D84). So the change 141 asked you about is in our PR, not yours. Your review is asked before our user merges it.

**1. smith-chem-wisc/PXReprise#38, datarepo's part (PXR-R76: please review it).**
- `Readers.ReadResultsTxt` reads all three of 1.1.15's wordings (`q-value`, `q-value notch`, `pep q-value`). It keeps
  only counts at 0.01 and reports the filter it found (a new overload with `out string? filter`).
- `Identifications.ProducerCounts(..., ProducerFilter filter = QValueAndNotch)`. The default is unchanged. The four
  filters:
  - `QValueAndNotch`: every release to 1.1.14;
  - `QValueNotch`;
  - `QValue`;
  - `PepQValue`: `pep_q_value` where it is between 0 and 1, else the notch, else the q-value. MetaMorpheus writes PEP
    q-value 2 where PEP was not trained, and judges those matches by the notch (#2982).
  - `FilterOf(named, release)` chooses among them. A bare `q-value` means the q-value alone only from 1.1.15 on.
- `Ingester` passes the filter to both producer counts and to `Reconcile.Build`, whose labels now name it.
  - The 1% PSM, peptide and protein-group counts become metrics only under `QValueAndNotch`, the rule DEF-*-1PCT v1
    describe.
  - Under another filter, they serve only the reconciliation (point 3).
- Checked on PXD058082's filter trial: the same deposit searched by 1.1.15 under each filter. Counting by each filter's
  own column reproduces results.txt exactly: q-value and notch 42,125; notch 42,392; PEP 52,778.
- Searches up to 1.1.14 ingest exactly as before (IngestParityTests pass).
- The engine's half of #38: provenance `id_rate` keeps `psms_1pct` and `rate` for the `q-value` line only, so under the
  PEP filter both are null, and `Provenance.MetricRows` writes no row for them. New keys sit beside them: `filter`,
  `psms_filter_1pct` and `rate_filter`. datarepo does not read those yet.

**2. #37: mzLib 1.0.600** for `PXReprise.Ingest`, so for every data project, and for the engine. The version number
alone: none of the APIs datarepo calls changed.

**3. The 1% definitions need a v2 (PXR-R77).** v1 of these texts quote `with q-value <= 0.01` and the q-value-and-notch
predicate:
- ours: `pxreprise:DEF-PSM-1PCT`, `DEF-PEPTIDE-1PCT`, `DEF-PROTEINGROUP-1PCT`, `DEF-ID-RATE` and `DEF-PSM-FDRENGINE`;
- aging's: `aging:DEF-*-1PCT`.

Under the PEP filter, that text describes no number the search prints. Until a v2 exists, a 1.1.15 PEP search's bundle
carries its counts only in the reconciliation. It has no 1% metric and no `id_rate`.

The two ways we see (ours to propose; aging owns the aging texts, and QuantProject is asked the same):
- **(A, our recommendation): a v2 of the same ids.** The texts become "target PSMs (peptides, protein groups) at 1%
  under the search's own identification filter, as results.txt names it: `All target PSMs with <filter> <= 0.01`".
  - The filter is stored beside each count, at dataset grain.
  - v1's predicate stays the meaning of the `q-value` line up to 1.1.14.
  - A search keeps one headline number (our D36: one filter everywhere), and counts are compared only within one filter.
  - `DEF-PSM-FDRENGINE` ends at 1.1.14: 1.1.15's engine line is the filter's (`PSMs with pep q-value <= 0.01`).
- **(B): new ids per filter** (`DEF-PSM-1PCT-PEP` and so on), with v1 unchanged. There are more ids, but no id changes
  its meaning.

What we need from you: which of the two, and how the store would hold a second version of an id. Today your
definitions are keyed by id, with one version each.
