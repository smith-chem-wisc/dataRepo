## PXR-R15: our plan for steps 1 and 2

### Measured on aging's store (a scratch catalog; the store was only read)

| | value |
|---|---|
| bundles (newest per deposit) | 109; 8.65 GB of Parquet, of which PSMs 6.97 and peptidoforms 1.25 |
| a catalog of views over them (16 tables, no PSMs) | 0.5 s to build, 1.3 MB |
| plus today's derived tables (`dataset_overview`, `protein_datasets`, `protein_index`, `search_modifications_placed`, `peptide_index`), our SQL unchanged | **17.1 s in all; catalog 39.3 MB** |
| `count(*)` over a view (41.3M quant values, 22.4M peptidoforms) | 0.02 s, from Parquet metadata |
| one dataset's quant values | 0.01 s; **1 of 109 files scanned**, although `dataset_id` is derived from the path |
| one protein's quant values across every dataset | 0.28 s (1,622 values, 42 datasets) |

- **At scale:** linear in deposits, 4,350 deposits would take about 11 minutes and 1.6 GB, just over both of your
  acceptance limits. Most of that is per-deposit (`protein_datasets` is one row per dataset and protein: 2.7M rows
  today). So step 2 computes those tables once per deposit, and a publish then only aggregates the corpus-wide
  indexes from them.
- **Two facts the design absorbs:**
  - 10 of the 17 bundle tables carry no `dataset_id`, and none carries `bundle_id`, so a view derives both from the
    file's path.
  - A table with no rows is not written (`sample_characteristics` is absent from 93 of 109 bundles), so a view
    unions the files that exist, and a table no bundle has is a typed empty view.

### Step 1, about a week: views, versioned files, a pointer

1. **Views instead of copies:** every bundle table, and the engine artefacts (go, logs), become views. The derived
   tables stay materialised, and they are small.
2. **`catalog-<catalog_id>.duckdb` plus `latest.json`:** a build writes a new file, then swaps the tiny pointer. No
   file a reader may hold is ever replaced. `build --keep <n>` prunes old files that no release names.
3. **Checks:** row counts come from Parquet metadata against `bundle.json`, plus the cross-bundle checks. The re-run
   of ingest's own integrity checks over every table is dropped: ingest already made them and recorded the result.
4. **`release_id`** beside `catalog_id` (rule 9; see PXR-R17), both in every MCP answer's provenance.
5. **The MCP server** opens through `latest.json`. Its sandbox (our D14) is adapted, as measured below.
6. **Parity:** the new catalog must answer like today's, row by row, on aging's store before anyone switches. The
   site is byte-compared.

### Step 2, about a week

1. **PSMs leave the catalog.** `dataset_overview` takes its PSM counts from `bundle.json`, and the `psms` and
   `psms_1pct` views, the PSM indexes and their prose go. PSMs stay in every bundle. We listed every reader: none
   needs PSM rows, only counts.
2. **Per-deposit derived tables** (`protein_datasets`, `search_modifications_placed`, the `dataset_overview` row) are
   computed once per bundle and stored beside it. The publish aggregates `protein_index` and `peptide_index` from
   them.
3. **Your batch runs `logs.resolve_genes` and `go.annotate_groups` right after each ingest,** instead of aging's
   publish running them every time. There is no code for us in that.

### Where we refine a rule (PXR-R17 asks you to accept or correct each)

- **Rule 5, "stored with the bundle": we propose *beside* it, keyed to it, not inside it.**
  - A bundle is immutable, and its id hashes its inputs.
  - GO annotation depends on go.obo and aging's category map, which change on go's and aging's schedule, not the
    deposit's. Inside the bundle, every go.obo release would make a new bundle of every deposit, and so a new
    release.
  - Beside it, as the content-addressed artefacts the runner already writes, the work is still done once per
    deposit and per input version, and the bundle never moves.
- **Rule 9, the release id: yes, and a second id for the catalog file.**
  - `release_id` hashes the sorted bundle ids and the schema version, as you wrote. It names the data.
  - `catalog_id` keeps hashing the builder's version too, because it names one catalog file whose views and
    derived tables are code.
  - Our standing rule is that anything reaching a written row is an input to the hash that names it. Two builders
    whose indexes differ must not share an id. The data's identity is still exactly your rule's.
- **Rule 4, a detail: absolute paths, one catalog per location.**
  - The MCP sandbox (D14) must stay. Measured: `SET allowed_directories = ['<store>/']`, then external access off,
    then the configuration locked, lets views read the store. Files outside, `..` traversal, unlocking and ATTACH
    are all refused.
  - But that check runs on the path as written, so a view with paths relative to the store is refused.
  - So a catalog's views carry absolute paths under one data root (`build --data-root <dir or URL>`). A hosted copy
    is a second build of the same release: same `release_id`, about a megabyte, seconds to write.
- **Rule 3: peptidoforms stay a view in the local catalog.** For hosting, the peptide tier can be a second catalog
  over the same release.

**Order:**
- Step 1, then step 2, each its own release, before 1.4.0's re-ingest (the ptmQtl engines and mzLib's ProForma
  change, which wait on an mzLib release).
- Neither step needs a re-ingest.
- Scheduled publishing (your rule 6) needs nothing from us.

## PXR-R16: DuckLake, adopt later

- **Maturity:**
  - Spec and extension 1.0 since 2026-04-13, declared production-ready.
  - Spec 1.1 and extension 2.0 are due 2026-10-21, tentatively.
  - It loads on our DuckDB 1.5.5.
- **What works:**
  - **No rewrite.** `ducklake_add_data_files` registered two bundles' protein groups, quant values and PSMs without
    copying them. Rows were identical, and every store file's sha256 was unchanged.
  - **Snapshots as releases.** One snapshot per registration, with a commit message, and `AT (VERSION => n)`
    returned exactly that snapshot's rows.
- **What rules it out under the store today: ownership.**
  - The docs say "the ownership of the Parquet file is transferred to DuckLake". We reproduced what that means,
    twice, independently.
  - **One default `CHECKPOINT`** merged the registered files into DuckLake's own and **scheduled the original bundle
    files for deletion**, including a bundle outside its data path. A later cleanup deletes them.
  - Orphan cleanup deletes every other bundle table under its data path.
  - That breaks your rule 1 (nothing published is ever modified), from one routine command.
- **Static hosting:**
  - A read-only attach over HTTP range reads worked only after we rewrote its metadata to relative paths by hand.
    Its API stores every path as absolute.
  - Files registered by `http://` URL could not be opened on Windows.
  - And `count(*)` still answered on that broken catalog, from metadata alone.
- **Also:** rows carry no `bundle_id`, and the release is a snapshot number, not a hash of its contents.
- **Recommendation:**
  - Keep rule 9's frozen list of bundle ids, written into the catalog.
  - Re-test DuckLake after spec 1.1, on ownership and relative paths.
  - If it is adopted, it holds a mirror, never the store.
- **Evidence:** our `design/PUBLIC_DATA.md` section 8 and `results/public_data_2026-10-11/ducklake/`.

## PXR-R8: several searches under one accession

**Not today.**
- The manifest is keyed by accession, and a second entry for one accession is refused. A catalog holds one bundle
  per dataset.
- Every id is prefixed by the dataset id: runs, assays, samples, PSMs, peptidoforms, protein groups, PTM sites and
  findings. So two searches of one deposit collide wherever both find the same thing.
- Runs come from the fetch manifest minus the provenance's `excluded_files`, so they collide unless each search
  excludes the other group's files.
- Downstream, one search per dataset is assumed by: the reconciliation against one `results.txt`, one
  `dataset_overview` row, the per-dataset indexes, and the site's `datasets/<id>.html`.

**With your rule 2 (a bundle keyed by deposit plus search configuration), we propose:**
- A deposit's only search keeps the bare accession as its key, so no stored bundle changes.
- Each search of a split deposit is keyed `<accession>-<group>`, for example `PXD052189-tmt` and `PXD052189-lfq`,
  from your corpus manifest. Every id then carries it, so nothing collides, and each search reconciles against its
  own `results.txt`.
- The catalog derives the accession and the group at build, so a deposit-level roll-up is a view.
- Our schema's `dataset_id` pattern (`^(PXD|MSV|JPST|IPX)[0-9]+$`) has to widen. That is a schema change, so it
  rides 1.4.0's re-ingest and costs no extra one.

**PXR-R18 (ask):**
1. The key form: is `<accession>-<group>` right for your corpus manifest, and what is the group vocabulary?
2. Can each search's fetch manifest or provenance list only its own files?
3. Keep split deposits parked until 1.4.0.

## PXR-R10: a dataset's database identity

- **Today:**
  - `dataset_databases` is built at BUILD from each bundle's record of the files it searched: dataset, bundle, file
    name, role (target or contaminant), sha256 and entry count.
  - `datasets.search_database` holds the target file's name. On aging's 112 stored bundles it is never the
    contaminant file.
  - Mixed kinds are already here: **16 of the 112 were searched against `*_all_genecentric_2026_03_agingPTM-v3.xml`
    and 96 against reviewed-only sets**, by file name.
- **We will not infer the kind from a file name.** That would turn your naming into our fact.
- **PXR-R19 (ask): a database registry from you, keyed by sha256.**
  - You build the databases (S20), so you know each one's facts: one row per database, with `sha256`,
    `uniprot_set` (`reviewed` | `canonical`), `uniprot_release` (`2026_03`), `proteome` (`UP000005640`),
    `organism` and your tag (`agingPTM-v3`).
  - Name it in the manifest. The build reads it into `dataset_databases` and onto `dataset_overview` as
    `search_database_set`.
  - Read at build, it covers every stored bundle as well as new ones, with no re-ingest and no schema change (our
    D32's pattern). A database the registry does not list reads NULL, meaning unknown.
  - It can ship in step 1's release.

## PXR-R11: what a canonical-searched dataset needs before delivery

- **Ingest: nothing.**
  - Ten-character TrEMBL accessions parse, and the searched file is hashed and checked as now.
  - `is_unique` comes from mzLib's classifier over the searched sequences, so it shifts as TrEMBL paralogs appear,
    as you said.
- **Engines:** a new target database means one `logs.resolve_genes` run per sha256, and `go.annotate_groups` runs
  once per bundle. aging's publish runs both for every dataset at each publish (idempotent), so canonical datasets
  are covered. After step 2, your batch runs them after each ingest.
- **The coverage check: agreed, a pass that lists gaps in its detail is easy to miss.** In step 1's release:
  - `build` prints an uncovered dataset as a warning, not a note;
  - `build --require-engines logs.resolve_genes,go.annotate_groups` refuses the build when any selected dataset lacks
    either.
- **The site:** once PXR-R19's column exists, each dataset page names its database set, and the generic tiles can
  be split by it. Whether aging's front page splits its figures is aging's call.
