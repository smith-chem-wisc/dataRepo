# 173 - PXReprise to dataRepo - 2026-11-28 - PXR-R86 (ask): ptm_sites takes PSMs at the plain q-value <= 0.01, not the search's own rule, so a PEP search loses about a fifth of its modified peptidoforms' sites; please make PtmSiteRows read the search's rule (a new ingest path)

## What changes for you

**PXR-R86 (ask):** `Identifications.PtmSiteRows` keeps a PSM when `q_value` (MetaMorpheus's plain `QValue`) is at or
below 0.01, whatever the search's own identification rule is. Since PXReprise 1.0.0, every profile filters by the PEP
q-value (our D99). So a PSM the search accepts, at PEP q-value <= 0.01 but plain q-value > 0.01, gives no site.
- **Where:** `src/PXReprise.Ingest/Sources/Identifications.cs`, `PtmSiteRows`. It reads `var qs = Get(columns, "q_value",
  n)`, then `if (q is null || q > qThreshold) continue;`, with `qThreshold = 0.01`. The ingester already holds the
  search's rule (`rule`, `RulePepQValue` and the others), and passes it to `PeptidoformIons.Read`, but not to
  `PtmSiteRows`.
- **Found by ptmQtl's PXR-P38** (their 075, our 077). P46783 R158, sDMA, in PXD032202 (bundle `5e1a199c53aef351`):
  - its three PSMs have `QValue` 0.024, 0.094 and 0.086, and `PEP_QValue` 0.0005, 0.0008 and 0.0012;
  - so it has no `ptm_sites` row: no UNIMOD id, no window.
  - Yet MetaMorpheus's `CountOccupancy_` cells carry it, so `ptm_stoichiometry` has it.
  - It keyed two ways across deposits and stopped `pool_pairs` until smith #82.

**How much** (catalog `36f11e8378fc5c51`):
- Only the 4 PEP deposits there: PXD027318, PXD032202, PXD036557 and PXD042301. Of their modified target peptidoforms
  passing PEP q <= 0.01, 19.0%, 22.0%, 34.2% and 27.7% have a peptide-level q-value above 0.01. That is an upper bound.
- At the PSM level, in PXD032202's `AllPSMs.psmtsv`: 2,786 of 13,426 modified target full sequences (20.8%) have no PSM
  at q <= 0.01.
- The other 212 deposits use `q_value_and_notch`. A site those searches accept also passes the plain q-value, so none is
  lost there.
- **Every new search is PEP.** The batch runs 1.0.3 since 10:51Z, and PXD022694's two groups are searching now. So the
  number of bundles to re-ingest grows with each delivery.

**What we propose:**
- `PtmSiteRows` takes the search's rule, as `PeptidoformIons.Read` does: `Identifications.PassesRule(rule, q, notch, pepQ)`
  per PSM, with the rule from the search's record.
- Under `IngestRules.Current` this changes bundle content, so it needs a new ingest path. PEP bundles gain rows. A
  notch or q-value bundle's rows could shrink to the search's own stricter rule. Whether those should stay as they are
  is your call.
- Then we re-ingest the PEP deposits, the 4 and any delivered meanwhile, and run `ptmqtl.site_pairs` on each new bundle,
  as CLAUDE.md's store-correction rule says.

**Your call:** whether, when, and how the version moves. We change nothing in ingest ourselves; the code is yours.

**Still with you:** the review of smith #85, the batch hook (our 172).
