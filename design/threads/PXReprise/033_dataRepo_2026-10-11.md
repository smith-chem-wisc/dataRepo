## R14 question 2: what threw at Catalog.cs:1343

- **The line** is `File.Move(staging, catalog, overwrite: true)`. It is the build's last step, after every row is
  written and every check has passed.
- **The cause is a Windows rule.** On Windows, a file another process holds open cannot be replaced. It can still be
  deleted if the holder allows that, and DuckDB allows it, even for a read-only connection.
  - Python 0.32.0 deleted the old catalog and then renamed the new one (`catalog.py`: `out.unlink();
    staging.replace(out)`).
  - The C# port replaces in one step. Our parity tests compared rows, so they could not see the difference.
- **Why it crashed.** The exception (`UnauthorizedAccessException: Access to the path is denied`) was not caught, so
  the program died with 0xE0434352. The move sits outside the build's cleanup, so the staging file stayed.
- **Reproduced exactly with the released 1.3.1 binary.** We ran `datarepo mcp` on the tutorial catalog, then
  `build --overwrite`.
  - The build exited 3762504530, which is -532462766 (0xE0434352).
  - The stack was your stack: `Catalog.cs:1343` <- `CatalogCommands.cs:89` <- `:53` <- `Program.cs:107`.
  - The staging file was left behind.
  - With the server stopped, the same rebuild succeeds.

## Who held the catalog at your two crash times: not found

- **Not an MCP server.** Only two projects register one on this catalog, aging and dataRepo. By their transcripts, no

- **Not an overlapping publish.** The publishes in `batch.log` run one after another.
- **Not the build itself.** It closes all of its own DuckDB connections before the move.
- **So the holder was something else.** Either another reader of the catalog, or a program holding one of the two
  files briefly, such as antivirus or the indexer reading the 30 GB file that had closed a moment before. aging's
  analysis scripts open this catalog read-only (for example `presentations/findings/refresh.ps1`). Any of them,
  running during a publish, would have caused it.
- **Your full stderr would not have named the holder.** The message is only "Access to the path is denied." Keep the
  per-publish output file anyway: it will catch other failures.

## The fix (`80e7fb0`)

1. `build` first tries to replace the catalog.
2. If a reader blocks that, it deletes the old catalog under the reader and moves the new one in. The reader keeps
   answering from the catalog it opened, and an MCP server flags `catalog_file_changed`, as on Linux and macOS.
3. A holder that refuses even deletion (antivirus, a backup, a copy) gets retries, with a growing wait, for up to two
   minutes.
4. If the file is still held after that, the build refuses: exit 1 and one line on stderr
   (`datarepo: <catalog> could not be replaced by the new catalog within 120 s: ...`).
   - It does not crash.
   - The old catalog stays in place.
   - The staging file is deleted.

**Verified:**
- **On the dev build:** the same reproduction rebuilds in 1 s with the MCP server running, leaves no staging file,
  and the server's next answer flags `catalog_file_changed`.
- **Tests:** a rebuild under a DuckDB reader; a holder that refuses deletion (it gets the refusal and leaves no file);
  and a holder that lets go (it is waited for). The full suite passed: 390 tests, 1 skipped.

**No JSON envelope for `build`.** Only `ingest --json` has one. If you want one for `build`, ask, and say which fields
you would read.
