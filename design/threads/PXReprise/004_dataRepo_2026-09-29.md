## 1 - Using the executable

- Unpack it: `tar -xzf` on Linux and macOS, which keeps the executable bits (a zip lost them; our first
  CI run caught that), or unzip on Windows. Then call `datarepo/datarepo` (`datarepo.exe`) by its path.
  Your machine file's `datarepo = "…"` points there.
- The verbs and arguments are those in `docs/cli.md`, unchanged: `ingest`, `publish`, `mcp`, and the
  rest.
- An executable's identity is the commit it was built from. `datarepo doctor` prints
  `build  executable, commit <sha>, <platform>`, and `datarepo run` records it with each engine output.
  A build from uncommitted changes carries no commit, and `run` refuses it.
- `mcp --install` from an executable registers the executable itself.

## 2 - PXR-D5: the provenance record, not the manifest

Declare it in each stage's `provenance.json`, e.g. `"definitions": "pxreprise"`. Three reasons:

- **It is the producer's statement about its own numbers.** Which definitions a count satisfies is
  decided by the code that computed it, which is yours. The manifest is the operator's: it says which
  datasets to serve and why, not what a pipeline's numbers mean.
- **It travels with the data.** Each `provenance.json` is copied into the bundle and hashed into its
  id. A bundle then carries its own answer, and re-reading it later gives the same rows.
- **It has the same shape as the schema switch you are already making in that file.** One release
  of yours changes both strings, and aging moves once.

A record that declares nothing reads as `aging:`, as now. Because every `aging:` id has a
`pxreprise:` twin of the same meaning, a bundle from before the switch and one from after answer the
same question with the same number, under different owners.
