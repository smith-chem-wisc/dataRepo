### 2. Layer and key

  - #26 already gives them the kind `engine:logs.register_orthology`.
- **The bridge (`protein_orthologs`) is the catalog layer.** It joins two of logs' artefacts to `protein_index`, and only

### 3. The accession index: a table in the catalog file, built per deposit

- **Yes, materialize it in the catalog file.** `protein_index` and `peptide_index` already are, in both layouts.
- **Build it as `peptide_index` is built:**
  - per-deposit rows in `derived/` (`DepositDerived.cs`), reused by every later build;
  - one table at build, sorted by accession, so DuckDB's zone maps skip all but a few row groups.
  - Every row is within one dataset, which is the rule `DepositDerived` needs.
- **Not one Parquet file in `derived/` for the whole corpus.** Each file there belongs to one deposit and is reused. A
  corpus-wide file would be rewritten at every build, and a one-file catalog could not read it in the MCP sandbox.
- **What it costs, measured** on aging's catalog `4e486c3dcf0aa01c` (210 bundles). We wrote a scratch file only, nothing
  to the catalog or the store (our `results/accession_index_2026-11-19/`):

| | |
|---|---:|
| target peptidoforms at 1% | 7,695,287 |
| index rows (one per accession of each) | 8,325,712 |
| accessions | 49,891 |
| (accession, dataset) pairs | 869,905 |
| one zstd Parquet file, sorted by accession | 108 MB |
| time to build it from the folder catalog | 42 s |
| one accession's lookup in that file, warm | 7 ms |

  - The columns were `protein_accession`, `dataset_id`, `bundle_id`, `peptidoform_id`, `base_sequence` and
    `best_q_value`. That comes to about 0.5 MB per deposit.
  - DuckDB's own storage will differ from Parquet's, so please give the table's size in the PR. The folder catalog file
    is 171 MB today.
- **Keep `base_sequence` in it.** Coverage then needs no second pass over `peptidoforms`.
- **For counts alone, `protein_datasets` answers now.** It holds each (dataset, accession)'s `n_peptidoforms` and
  `n_protein_groups`, and the catalog indexes it on accession. "Which deposits, and how many peptidoforms" needs no new
  index.

### 4. Protein sequences: an engine run per database file

- **Nothing holds them today.**
  - The ingest reads every searched database to place sites (`ProteinDb.Load`, `Ingester.cs:528`). It hashes each file
    into the bundle as a source, but copies no sequence.
  - A bundle keeps only `ptm_sites.sequence_window`: 15 residues around each site.
- **The key is one file's sha256, plus the reader's version.**
  - A sequence is a fact of one file, so per-file keying is right here. Whether it is right for GO is PXR-R73.
  - The reader's version goes in the key, as logs asked on #25: one file read two ways gives two artefacts.
- **Read them as the ingest reads them,** because coverage must use the sequences the sites were placed on.
  - The ingest's reader is deliberately not mzLib's loader. With its defaults, the loader adds variant proteins (264
    contaminant entries become 579; `ProteinDb.cs:151-157`).
  - logs' engine loads with `maxHeterozygousVariants: 0` (`LogsEngine.cs:167-171`). The two may agree, but that is
    to be measured, not assumed.
- **A build checks them against the bundles.** Every `ptm_sites.sequence_window` must equal the window cut from the
  stored sequence at `position`. A failure fails the build, as #26's checks do. This check is what ties the table to the
  positions already stored.
- **An accession with two sequences is a row, not a choice.** Two files of one search can carry an accession with
  different sequences (the ingest's `Ambiguous` case, such as a target and a contaminant copy). The coverage answer then
  says so, with a reason, as `protein_orthologs.status` does.
- **Give each row a `sequence_sha256`.** logs' coming residue rows are keyed `(accession, sequence_sha256, position)`
  (their 037, from their 033), so they would join this table directly.
- **It comes from an engine, not from the build.**
  - The runner takes each file by sha256 and records it, as it does for `logs.resolve_genes`. The catalog copies the
    artefact's rows. A build reads only the store.
  - For aging that is one run per distinct searched file: the 42 target files of our 131, plus the contaminant panel.
- **It gets a layer of its own,** with a `reference` key. Its reader changes with the ingest, not with logs or GO. That
  is logs' argument on #25 for keeping layers apart.
- **Its size is unmeasured.** Please give it in the PR.
