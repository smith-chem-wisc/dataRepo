# 158 - PXReprise to dataRepo - 2026-11-25 - datarepo-binaries is green on master again (smith #63, 8fc5ae8): the engine's osx-arm64 publish was the failure, not datarepo. Nothing asked

## What changes for you

- **`datarepo-binaries` had failed on every push to master since #43** (decision 0073, d4f8b3c, 2026-11-22). That PR
  made the workflow publish the engine beside datarepo on four platforms. The osx-arm64 job stopped at Microsoft.ML
  3.0.1's build targets: "Microsoft.ML currently supports 'x64' and 'x86' processor architectures".
  - **The failing project was the engine** (`src/PXReprise/PXReprise.csproj`). mzLib 1.0.601 carries Microsoft.ML for
    FlashLFQ.dll, the only mzLib assembly that names it. Microsoft.ML's targets refuse an executable built for arm64.
  - **datarepo was never affected.** Its osx-arm64 publish passes, before the fix and after.
- **The fix, smith #63, merged 16:21 UTC as 8fc5ae8.** One property in the engine's csproj,
  `EnableMLUnsupportedPlatformTargetCheck=false`, with a comment.
  - **Why it is safe:** the engine never runs Microsoft.ML code. It reads FlashLFQ's types only, and MetaMorpheus
    quantifies as its own process. A probe after the whole offline suite found FlashLFQ loaded and no Microsoft.ML
    assembly.
- **Master's `datarepo-binaries` run on 8fc5ae8 passed on all four platforms**, the first pass since 2026-11-22.
  On osx-arm64, both programs ran with no .NET on PATH and again from the unpacked archive. The 1.0.0 tag
  (release.yml runs the same steps) no longer has this in its way.
- **Also merged today, for your information:** smith #61 (79ede19), a `labels` verb for ptmQtl (decision 0094). It
  labels each run's sample type and each search's cysteine chemistry, and writes `07_labels/labels.json` in the
  deposit's folder. It changes no bundle and no ingest. Where those labels should live in the bundle is a question we
  will bring you separately, as a proposal.
