## Released (in mzLib 1.0.594, so carried by MetaMorpheus 1.1.12)

### 1. mzLib #1345: read current FlashLFQ peak tables

- **PR / sha / release:** mzLib #1345, merge `0cd946459`. First in 1.0.592, also in 1.0.593 and 1.0.594.
- **What it does:** `Readers.QuantifiedPeakFile` loads an `AllQuantifiedPeaks.tsv` written without the `MBR Score`
  column (every FlashLFQ since #802, including MetaMorpheus 1.1.11 and 1.1.12), and reads the seven current columns
  (`Organism`, `Peak FWHM`, `Peak FWHM Status`, `PIP Q-Value`, `PIP PEP`, `Decoy Peptide`, `Random RT`).
- **How to switch it on:** nothing to switch. Use `new QuantifiedPeakFile(path)` or `FileReader.ReadFile<QuantifiedPeakFile>(path)`.
- **Recommendation: not for the pipeline search.** It changes nothing in the search. It matters only if PXReprise's own
  C# reads `AllQuantifiedPeaks.tsv` through mzLib. In that case it already works on 1.0.594, and no action is needed.
  Ask: **PXR-DR1**.
- **Traps:** `MBRScore` is now `double?`, and so are the PIP columns. They are null when the column is absent, and on
  MSMS peaks. Do not coalesce null to 0. Writing a table back emits the union header of both formats, which reads
  back correctly but is not byte-identical to FlashLFQ's file.

### 2. mzLib #1346: ProForma computed from Full Sequence when the psmtsv has no ProForma column

- **PR / sha / release:** mzLib #1346, merge `cbd6db4ee`. First in 1.0.592, also in 1.0.593 and 1.0.594.
- **What it does:** `SpectrumMatchFromTsv.ProForma` (so every `PsmFromTsv`) converts `Full Sequence` to ProForma with
  UNIMOD accessions on first access when the file has no `ProForma` column, or a blank cell. It returns null for an
  ambiguous (`|`-joined) sequence, and never throws.
- **How to switch it on:** nothing to switch. Read `psm.ProForma` on a record from `SpectrumMatchTsvReader` / `PsmFromTsvFile`.
- **Recommendation: not for the pipeline search.** It changes nothing in the search. MetaMorpheus 1.1.12 still writes a
  `ProForma` column for **top-down** runs only (`PsmTsvWriter.cs:205`), so for bottom-up `.psmtsv` the value comes from
  this reader. Ask: **PXR-DR2**.
- **Traps:**
  - **Lazy and not free.** The first read of `ProForma` loads mzLib's modification databases.
  - **The string depends on the mzLib that reads, not the one that searched.** mzLib #1403 (merge `57a4b0d5b`, in
    1.0.594, origin `bridge`) makes UniProt-named mods write their UNIMOD id. So the same 1.1.11 `.psmtsv`, read with
    1.0.592 or 1.0.594, gives different ProForma for those mods (`[UniProt:N-acetylalanine on A]` in 1.0.592 becomes a
    `UNIMOD:` id in 1.0.594). This is a reader-version effect, not a search change. dataRepo handles it on our side with
    a new ingest path and a re-ingest (our D46, aging 096). You need do nothing for it, but do not diff ProForma
    strings across reader versions and call the difference a 1.1.11 vs 1.1.12 search difference.
  - Ambiguous rows are null. A disambiguated copy (`new PsmFromTsv(psm, candidate, i)`) converts its own candidate.
