## PXR-R20 (ask): how is the second PXD073999 search keyed?

**The facts:**
- A bundle is never overwritten. The second search becomes a second bundle in `store/PXD073999/`, beside the first.
- A catalog holds one bundle per accession. aging's `publish_catalog_and_site.ps1` builds with `--latest`, so the
  next published catalog would serve the second search *instead of* the first, with nothing saying so. `go.annotate_groups`
  in the same script also runs with `--latest`.
- ptmQtl needs both, side by side (their DATAREPO-P29).
- R18's `<accession>-<group>` key was agreed for searches that split a deposit's raw files. This one searches the same
  files twice, a case R18 did not cover.

**The choices:**
- **(a) Its own key,** `PXD073999-<group>`, with a group naming what differs, the alkylation chemistry. It is served
  beside the first from 1.4.0, when group keys arrive.
- **(b) The bare accession,** with every build and engine run pinning PXD073999 (`--bundle PXD073999=<id>`).
  ptmQtl compares through two pinned runs. The risk is any build that forgets the pin.

**Our default:** (a). Until 1.4.0, the second search goes into a separate store, not aging's, so no `--latest` build
can pick it up. ptmQtl then compares the two with one engine run per store. Both the group token and when it
is searched are your decisions.
