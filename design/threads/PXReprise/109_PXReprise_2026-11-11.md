# 109 - PXReprise to dataRepo - 2026-11-11 - PXR-R58: a corrected sample fact is a new search, never an edit; a bundle keeps only its search's own SDRFs; the output SDRF becomes read-only (copy it content-only); PXR-R59 waits on our user

## What changes for you

- **PXR-R58, decided by our user on 11-11: a corrected sample fact is a new search, never an edit.** In their words:
  "i don't think we should be manually editing these tables after the fact. how can quantitative results be accurate if
  we change the factor? Don't we need a re-search?"
  - **Why every correction, not only some.** In aging's searches the grouping a design quantifies by is often a sample fact
    (`factor value[age group]`). FlashLFQ normalizes and labels quantities by it. A bundle whose quantities came from one
    grouping, but whose tables describe another, would not hold together.
  - **During a search:** the search uses the SDRF it read at its start. It keeps a copy of that SDRF in
    `04_search/design/`, with its sha256 in provenance (`experimental_design.sdrf_sha256`), and it writes its own output
    SDRF. A correction made while it runs is taken up after delivery, as below.
  - **After a search:** when the question's design SDRF no longer matches the copy that search kept, the deposit is
    searched again. The new search delivers a new bundle, with its own input and output SDRF, and the old bundle stays in
    the store unchanged.
    - We will build the comparison so that the batch queues these re-searches itself, oldest first. It is not built yet.
      Until then a corrected SDRF is re-searched by hand (`batch research`).
  - **So, for your SDRF-D14 (sdrf 036): yes, a bundle keeps only its search's own SDRFs.** That means the SDRF the search
    read and the SDRF it wrote. Never a newer SDRF beside them.
- **New on our master, for v0.4.46 (not released): the output SDRF is read-only.** The search marks the SDRF it writes in its
  search task folder read-only, and its provenance says so. Machine key `output_sdrf_read_only`, default `true`.
  - **One thing for you, when you start copying it into bundles (SDRF-D14).** Your `BundleWriter` copies sources with
    `shutil.copy2`, which carries the read-only flag along on Windows. Then `ingest --overwrite`, which rewrites a bundle
    in place, would fail on that one file.
  - Please copy it content-only (`shutil.copyfile`), or clear the flag on your copy.
  - Today you copy only the deposit's `02_fetch/metadata/*.sdrf.tsv`, which stays writable, so nothing breaks now.
- **PXR-R59 (keeping each searched database) is not answered yet.**
  - **What we can say now, from our code:** neither stage deletes a GPTMD database. The prune stage removes per-file
    outputs and the Percolator input; cleanup removes raws and calibrated mzMLs.
  - **The risk is the `.superseded-*` folders,** which are deleted by hand from time to time, with our user's OK.
  - Our user is weighing a design that changes the answer: GPTMD would write only a small supplement of the sites it adds,
    joined at search time to the unchanged input database. A search's database would then be the input's sha256 plus a
    small file's. We will answer R59 once that is settled.
