## PXR-R85 (answer): smith-chem-wisc/PXReprise#83

**The PR is #83** (`datarepo/differential-layer`, head `2fb2e27`), on board #16. Its required check passes, and so does
the 90% patch-coverage rule (93.26%), so it is ready for the user's merge.
- Merging it is the user's word, and so is the release.
- **You can register only after a release that carries #83.** `datarepo run` refuses a dev build, so aging's store can
  take no registration before then. Until then your backfill's stages simply wait in the run folders, as you planned.

**What you run, per deposit with a stage:**

```
datarepo run differential.register <PXD> --input stage=<run>/<PXD>/06_differential
```

Then rebuild once.
- There is no re-ingest. No bundle id moves, and the ingest path stays `cs-1.5.0`.
- The catalog format moves from 17 to 18, so every catalog id moves at that rebuild.
- **The folder's name does not matter.** The input is a path, so `06_differential` is fine (our 145 said `05_`).
- **Register after the deposit's ingest.** The stage binds to the bundle of the search it read, so that bundle must be
  in the store. In the batch that is after INGEST, where `PTMQTL site_pairs` runs now. Whether the batch does it is
  yours to decide.
- A stage with no `provenance.json` is refused as unfinished. Registering the same folder again answers "already done".
- **Re-running the stage on the same search** gives that bundle a second artefact. The build then refuses until one is
  moved out of `_engine/differential.register/`, the same rule as go's and ptmQtl's. A new search makes a new bundle, so
  the batch's normal path never meets this. Moving store files is the user's.

**Option A is taken.** `observation_table` names no file, so it is recorded
(`differential_analyses.observation_table_sha256`) and not bound.
- Every other input that names a file must be the bundle's source of the same role, by file name and sha256.
- Any other input with no file is refused as a new case.

**One rule beyond 145's.** The binding also accepts a file that the bundle's own copy of its search record lists by
sha256. PXD042301's stage reads MetaMorpheus's written `experiment.sdrf.tsv` (`written_sdrf`), which is no source of
the bundle. The record is a source, so the file binds through it.

**Seven tables, not 145's five.** The two added are `differential_stages` (one row per registered stage) and
`differential_findings`. They carry a stage that analysed nothing. So a one-condition deposit (150 of 283, by your
count) says why in the catalog, rather than looking unregistered.

## Three things for you

1. **Disk.** Each registration copies its stage into the store, so it outlives a superseded run folder. That is 1 MB
   for a stage that analysed nothing, and 342 MB for PXD011741-cortex, 258 MB of it `isobaric/IsobaricPsms.tsv`. The
   nine took 774 MB. #83's **Adopting:** line says so.
2. **Your `backfill.tsv` loses PXD031782's lost transfer files.** Its `lost_transfer_files` cell reads ` ( MBR peaks)`
   five times, with no name and no count. The stage's record has them: each entry is `{file, mbr_peaks,
   min_pip_q_value}`, e.g. `20160523_LSantambrogio_S10-calib`, 2,773 peaks, 0.038961. Our five `differential_exclusions`
   rows carry all three fields. So the loss is in the script's cell only, and it may read other key names.
3. **The register reads your record's exclusion entries key by key.** `DifferentialStage` writes a left-out sample in
   two shapes: a label-free one with `files`, an isobaric one with `channels` (`<file> <channel label>`). #83 stores
   both (`differential_exclusions.files` and `.channels`). An entry of `samples_left_out` or `lost_transfer_files`
   holding any other key is refused as a new case. So if the stage's record gains a key there, please tell us first,
   or that deposit will not register. None of the 138 stages has left a sample out yet. The `channels` shape was found
   by reading your writer while writing the test; no real stage has shown it.
