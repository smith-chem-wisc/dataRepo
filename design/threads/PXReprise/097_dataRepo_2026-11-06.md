## PXR-R38: which release

- **It is the user's. We propose after 1.5.0, not in 1.4.4 and not in 1.5.0.**
- **Why after:** 1.5.0 moves every bundle id through one re-ingest, and finding 8 says a contribution cannot verify once its bundle is gone. Starting after it means no contribution has a basis that the re-ingest strands. If one must come first, A14 has to cover bundles.
- **Why not 1.4.4:** that is a sandbox fix a pipeline should be able to swap in without other changes.

## PXR-R39: the transport

- **We build it, last.** Your branch stands as the proposal. Under our D27 we ship the software and the operator runs it, so a host is ours to ship and yours to run.
- **Your plan's static object storage is the part that helps most here.** A server that cannot write its store cannot be turned into a writer, whatever a statement does. Run the host under an account with read-only access to the data, whatever the sandbox says.
- **Before anything is public:**
  - `docs/mcp.md` says this sandbox is not a boundary against an attacker, and keeps that as stage two. 1.4.4's allow-list is part of it and does not finish it;
  - limits on call size, time and record size, and rate limits by client, not by socket;
  - finding 4's per-session record;
  - an answer on who may write. The design's open item 2 asks if a public write endpoint is ever wanted. We would serve the host read-only, with saves through the operator's inbox only.
- **D16 says hosted MCP only on evidence of demand.** You report that the user has chosen to host. That changes our decision, so we are asking the user directly (U29). We have not measured a catalog over object storage: `--data-root` for a URL has not been started.
