# 001 - PXReprise to dataRepo - 2026-09-29 - A stranger's PXReprise install stops at the search because dataRepo cannot be installed without Python; get dataRepo ready for public use, generic, under the PXReprise umbrella

## What changes for you

This is the user's direction, relayed: **get dataRepo ready for public use, generic, and installable as part of
PXReprise.** The user's own words: "dataRepo should probably not be python ... I'd like dataRepo installed under the
umbrella of pxreprise." How you get there is your call. Below is what PXReprise needs, and why now.

## Why now

- **PXReprise is public:** `smith-chem-wisc/PXReprise` (MIT), docs at https://smith-chem-wisc.github.io/PXReprise/. It
  is a generic engine: a question is data, and aging is only the first question. Type 2 diabetes and single-cell come
  next.
- **The first-run test worked on a clean box.** On 2026-09-29 the user ran it on a fresh machine (fresh clone,
  MetaMorpheus release zip, template machine file, `examples/first-run`). It finished in 55 minutes, but it **stops at
  the search**. No dataRepo bundle, no catalog, no site. The user: "if someone wants this to work, they need the whole
  tamale."
- **The binding rule (PXReprise D8):** a new user needs only .NET 10, git and MetaMorpheus. They must not have to
  install a particular Python version or its packages. Python is acceptable only for optional, lab-internal extras.
- **Today dataRepo breaks that rule.** It is Python 3.11 with duckdb, pyarrow, PyYAML and optionally `mzlib`/lxml.
  - It installs only from a source checkout, and there are no GitHub releases.
  - The PyPI name `datarepo` belongs to someone else (v1.0, not ours).
  - On the aging box it runs from a venv (`F:\aging_batch\venv-0.21.0\Scripts\datarepo.exe`).

## Asks

**PXR-D1: installable with no Python on the user's machine.** You choose how:
- a port, since the user thinks dataRepo "should probably not be python";
- or a self-contained executable per OS attached to each release.

What PXReprise needs either way:
- one download a stranger unzips and points at (`datarepo = "..."` in their machine file);
- the same verbs, run as a process: `datarepo ingest <manifest> <accession>`, then build/catalog/site;
- Windows, Linux and macOS.

**PXR-D2: generic, not aging-shaped.** A new question must never need a dataRepo code change, just as it never needs a
PXReprise one.
- A grep of `src/datarepo` finds "aging" in 24 files: `definitions.py` 32, `catalog.py` 21, `mcp.py` 16,
  `identifications.py` 16, `ingest.py` 14, `runner.py` 14, `site.py` 14, and more.
- Some of those hits are only examples in docstrings; others are real coupling. Please sort which is which.
- **The provenance schema name `aging-provenance/3`.** PXReprise emits it because it is the only schema your ingester
  accepts. A neutral name (e.g. `pxreprise-provenance/1`), with `aging-provenance/3` still read for existing bundles,
  is the change our communication plan held back for "the second question". That time is now.

**PXR-D3: public releases under the PXReprise umbrella.**
- Versioned releases, with the binaries of D1, in a public home that sits with PXReprise. PXReprise's docs and its
  `getting-started` install step will pin a dataRepo version, as they pin MetaMorpheus 1.1.11.
- Which org or repo, and whether `trishorts/dataRepo` moves, is for the user and you to settle. Tell us what you pick.
- Please keep the release name clear of the PyPI `datarepo` collision.

**PXR-D4: a generic publish step we can put in `examples/first-run`.**
- Today aging's `[publish] command` runs its own `instance/publish_catalog_and_site.ps1`.
- A stranger needs a dataRepo verb, or a documented argv, that turns a manifest into a local catalog and a static site
  with no question-specific script.
- When D1 to D4 land, PXReprise will:
  - give `examples/first-run` a `[publish]` section;
  - add the dataRepo download to `getting-started.md`;
  - rerun the clean-box test end to end: search, ingest, catalog, site.

## What PXReprise will not do

- Port dataRepo into the engine. Bundles, catalog and study layers stay yours (OWNERSHIP.md), run as a process.
- Change the ingest call itself (`datarepo ingest <manifest> <accession>`, 3 h timeout) unless you ask.

Aging's running batch is not affected by any of this. It keeps its pinned venv until you release, and then moves when
aging chooses.
