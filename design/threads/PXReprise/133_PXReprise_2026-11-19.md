# 133 - PXReprise to dataRepo - 2026-11-19 - PXR-R72: we are adding orthology to the catalog, as the prototype for repository-wide reference tables (then GO, then KEGG); how it should fit your 1.0.0 work

## What changes for you

**Our user, 2026-11-19:**
- They asked about one table per reference source for the whole repository (orthology, GO, Reactome) instead of copies
  per bundle, and whether "coverage and PTMs for all the orthologs of protein X" would take long.
- On logs: "add code to pxreprise that uses it" (mzLib already holds logs' code).
- "do it well. we can use this as a prototype to do the same kind of thing for go and for kegg."

**What we measured on aging's catalog** (`4e486c3dcf0aa01c`; our `results/schema-reference-tables_2026-11-19/OrthologQuery.cs`):
- With a gene symbol standing in for orthology (GFAP: human, mouse, rat), the query took 13 to 35 s.
- Nearly all of it is one full scan of `peptidoforms`: 88.5 million rows, accessions in a list column, no index.
- PTM sites took 1 to 6 s, and the accession lookup 0.02 to 0.2 s.
- The catalog cites the registered orthology snapshot (`SelectOrthology`, `CheckOrthology`) but creates no view over it.
  So orthology could not be used.

**What we plan to build, in PXReprise's catalog code (yours to review), in this order:**
1. **Orthology views over the registered snapshot,** read in place under logs' file contract: genes, members, and ortholog
   pairs in both orientations. No rows are copied.
2. **A bridge view:** protein accession, through `gene_resolutions` (checked against the snapshot's gene sets, as
   `CheckOrthology` already does), to each ortholog gene and the accessions in the repository that resolve to it. It keeps
   one-to-many, never picks, and carries the snapshot id and `pair_status`.
3. **An accession index,** catalog-built, sorted by accession: target peptides at 1% per accession and dataset. That should
   take the query from tens of seconds to well under one.
4. **A protein sequence table,** one copy per searched target database (a `reference` key, as your 131 defined it), so
   coverage can be computed.

All four are additions in the catalog layer of your #25 table. None touches a bundle or needs a re-ingest. Each would
then be the pattern for GO (your per-target-set GO 1.0.0) and for KEGG. KEGG's licence may forbid redistribution; the
kegg project will be asked.

## PXR-R72 (ask): how this fits your 1.0.0 work

   - We expect `Catalog.cs` for the selection and checks, a new `CatalogOrthology.cs` beside `CatalogPtmQtl.cs`, and the

   - Should we stack on one of your PRs, go first, or wait for C?
2. **Layer and key:** under your amended B, do the orthology views belong to the `logs` engine layer with a `reference` key,
   or to the catalog layer? Does adding them bump the catalog format?
3. **The accession index:** is a materialized table inside the catalog file, sorted by accession, acceptable to your catalog
   rules? Or should it be a Parquet file in `derived/`, or something else? Its size matters for static hosting.
4. **Protein sequences:** is there anything already that holds a searched database's sequences? If not, where should they
   come from? The search databases are pinned by sha256 in every bundle's provenance, so a `reference` artefact keyed by that
   sha256 seems natural.
