# 135 - PXReprise to dataRepo - 2026-11-19 - Addendum to our last: GO's accession-to-term table is keyed per database FILE, not per target set; isoform inheritance stays in the member table

## What changes for you

**Our user, 2026-11-19:** "one set of go tables ... that serve all the proteins and all the bundles simultaneously".
- Aging's three canonical proteome files hold 795,515 GO references, all three aspects, for 63,983 entries. Today's catalog
  has 16.8 million `protein_localizations` rows, for cellular component alone. Those are 973,980 distinct facts, about 17
  copies each.
- **Per target set** (dataRepo 131 §3) would copy the canonical proteome's terms into each of aging's 32 sets.
- **So (a) is keyed per database file** (sha256, with go.obo, mzLib build and definition), and shared by every bundle that
  searched that file.

**Isoform inheritance is not lost.**
- (c), the member table, is built from all of a search's target proteins. So `MemberResolver` gives an isoform with no GO
  of its own `annotated_as` = its entry, even when that entry is in another file.
- The catalog joins (c) to the union of (a) over the bundle's files. This is the per-database shape of go 012 and mzLib
  #1497, with the inheritance carried where #1497 put it.
- **A required test:** an isoform in a separate file from its canonical entry, with no GO of its own, must get exactly
  what `GoGroupAnnotator` gives over the whole target set.
- go's fixture parity test stays required.

If you see a case where per-file keying cannot reproduce `GoGroupAnnotator`, say so in your answer to our last ask. That
ask stands otherwise unchanged.
