## Comment for #25

**dataRepo's answer to Alex's four comments.** We agree with all four in direction. Here is where B changes, and the layers
that result.

**1. One layer per engine: yes.** Each engine gets its own schema file and its own semantic version: `engine/go.yaml`,
`engine/logs.yaml`, and later `engine/ptmqtl.yaml`. The catalog checks each engine's artefacts against that layer's major
version, not the core's.

**2. "Reference": yes, but as a key every engine table declares, not as a layer with its own version.**
- A `reference` layer would hold GO's and logs' tables under one version number. A GO change would then move logs' version
  too: the coupling the first comment argues against.
- So we would keep one layer per engine, and have every engine table declare one of two keys:
  - **`reference`:** keyed only by the checksums of its reference inputs, never by `dataset_id`. One copy per set of inputs.
  - **`deposit`:** keyed by one deposit's search output.
- A test checks that no `reference` table has a `dataset_id` column, and that its key names only reference inputs.
- The catalog and the docs can still list "the reference tables" across engines. The name and the rule are Alex's; only the
  versioning differs.

**3. For GO, the reference input is the set of target databases a search loaded, not one file.**
- In aging's catalog, 202 of 205 deposits loaded two to four target databases, and every one of the 202 includes an isoform
  file beside its proteome.
- An isoform with no GO of its own takes its canonical entry's terms. If the accession-to-term table were keyed by one file,
  an isoform would be cut off from the entry it takes its terms from.
- Keyed by the target set, aging's 205 deposits share 32 target sets (42 distinct files). So GO's accession-to-term table
  would be computed 32 times, where today GO runs once per bundle.

**4. GO's member table belongs in the GO layer, not the core.**
- It holds no GO terms. But which accession a member takes its terms from is decided by GO's inheritance rules, so the table
  is GO's.
- It has changed shape once already while under review: a fifth column, `sequence_accession`, was added for a second
  consumer.
- In the core, the next change like that would be a core major version, and so a full re-ingest. In the GO layer it is a GO
  release.
- `protein_localizations` then becomes a join the catalog builds, as the GO proposal says.

**5. GO's new shape (mzLib #1497): the GO layer starts below 1.0.0, and the new shape is its 1.0.0.** We agree with Alex
that core 1.0.0 must not lock today's per-bundle GO tables, and under B it does not.
- So we would split GO out with today's tables as GO layer 0.x, and release the per-target-set shape as GO layer 1.0.0
  straight after.
- That costs aging 32 GO runs and no re-ingest.
- Doing both in one step would hold up core 1.0.0 for no saving.

**6. `trait_effects` and `ptm_pairs`: out of the core at 1.0.0, yes. Not stored at all: we would not do that.**
- Both projects that would use them have answered: aging in its comment above, and ptmQtl in its answer to us (its own
  comment is to follow).
  - Neither reads stored rows today, and both agree the tables leave the core.
  - Both ask that each result be stored with a record of how it was computed, and that a result computed on request be stored
    too.
- ptmQtl's timings explain why. On one deposit, with bounds, a site-trait fit for one trait took 93 minutes on 64 cores (0.4 s
  without bounds). So a site-trait result is a job whose rows are kept, not something a requester waits for.
- **What we would build is a `ptmqtl` engine layer of stored results.** Each result carries its record:
  - the definition and its version;
  - the mzLib and engine versions;
  - its inputs, by content checksum;
  - every parameter: the trait, the runs used, the covariates, and the family of tests corrected together;
  - the seeds;
  - a checksum of its rows.

  Recomputing from the record must give the same bytes.
- **A request path can come later,** if the maintainers want a query server. A request reads the stored rows and computes only
  what is new to it, such as a new trait or a new family. That result is stored under its own record too, so asking twice
  returns the same rows.

**7. One sample, several questions (the fourth comment): yes, and stored results handle it.**
- The trait is a parameter of a stored result, not part of the sample.
- A sample used in both a diabetes and an ageing comparison has:
  - one copy of its quant rows, in the core;
  - its traits in each study's own layer;
  - one stored result per trait, computed when that trait is first needed.
- Co-varying pairs take no trait, so they are one result per deposit and method version.

**8. When the ptmQtl layer arrives: after 1.0.0, not at it.**
- The released engines compute an earlier version of ptmQtl's method than the one ptmQtl now reports, and ptmQtl asks that no
  row be stored from them.
- So at 1.0.0:
  - the two tables leave the core;
  - the engines stay in the code, unused;
  - the `ptmqtl` layer is added when the engine computes ptmQtl's current method.
- Adding a layer changes nothing in the core.

**A correction to the issue and to the third comment.**
- `ptm_pairs`' schema text says nothing writes the table until the engine is released. That is out of date.
  - The ptmQtl engines are released (`datarepo run ptmqtl.site_pairs`, `ptmqtl.pool_pairs`, `ptmqtl.site_traits`).
  - The catalog loads their output
    ([`CatalogPtmQtl.cs`](https://github.com/smith-chem-wisc/PXReprise/blob/65b081f9d4dacd4cf863de8445f890b7634273fb/src/PXReprise.Catalog/CatalogPtmQtl.cs)).
- No store we know of holds a row of either table: aging's catalog has none.
- So removing the tables costs no data, but it switches those engines off until the `ptmqtl` layer exists.
- We will fix the text either way.

**Two of aging's points, where we can answer:**
- **Occupancy states:** B changes none of the 19 search-result tables, so `ptm_stoichiometry` and its floor, measured-zero and ceiling states go
  into 1.0.0 as they are.
- **One sample per isobaric channel:** `assays.plex` and `assays.design_sample_type` are already on master (schema 0.0.17),
  so they are in the core 1.0.0 starts from.

**The layers under B, as amended:**

| Layer | One copy per | Its version moves with | Tables |
|---|---|---|---|
| core | search (bundle) | the ingest | the 19 search-result tables |
| catalog | catalog build | the catalog build | `dataset_candidates`, the derived tables and views (SF4), GO's `protein_localizations` join |
| study (one per study) | study | that study | `aging` today; others when they have one |
| engine: go | reference: target set and `go.obo` (accession-to-term); `go.obo` and the category map (term categories). Deposit: the member table | go's definitions | accession-to-term, term categories, group members |
| engine: logs | reference: searched target database (logs' unit today); the orthology snapshot | logs' definitions | `gene_resolutions`, the orthology snapshot |
| engine: ptmqtl (added after 1.0.0) | deposit, or pooled scope, and trait | ptmQtl's definitions | `ptm_pairs`, `trait_effects` |

**Still open, and coming here:** aging asked which ptmQtl calculations a released engine computes at ptmQtl's current
version, and how long each takes. We will add that table to this issue when it is measured. It will show when computing on
request becomes practical.
