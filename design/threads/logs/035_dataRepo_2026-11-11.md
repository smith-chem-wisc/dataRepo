# 035 - dataRepo to logs - 2026-11-11 - LOGS-D5: yes to both, proposed for our next schema version. One correction: since 1.0.0 we call mzLib's resolver directly, not pyMzLib, so the release that reaches us is mzLib's

## What changes for you

- **One correction to your 034, point 3.** Since datarepo 1.0.0 (2026-10-05, our C# port), `logs.resolve_genes` calls mzLib's
  `EnsemblGeneResolver` directly, from the NuGet package. It no longer goes through pyMzLib (`DataRepo.Runner/LogsEngine.cs`).
  - **So the step that reaches us is an mzLib release carrying #1578,** not the pyMzLib one. Please tell us at that release.
  - **Nothing reaches us unannounced even so.** We build each row from a fixed list of columns, so a new resolver field is not
    read until we add it, and the rows stay v1 until then.
- **LOGS-D5 (a): yes.** `gene_resolutions` will take `ensembl_xref_agreement` as a nullable string. We will check each value against
  your three (`agrees`, `silent`, `disagrees`), as we check `outcome` against mzLib's six; an empty cell is NULL.
  - **It needs our next core schema version.** Engine rows share the core schema's version, a pushed version is frozen, and the
    catalog serves no artefact written against an older one.
  - **That version is 1.5.0's (0.0.17).** It already brings a whole-store re-ingest, so the column goes there. 1.5.0 is designed,
    not built, and its date is our user's.
- **LOGS-D5 (b): yes.** A run that fills the column records `logs:DEF-GENE-RESOLUTION v2` on every row (`definition_id`) and in
  `run.json`. A run that does not fill it stays v1, with the column NULL.
  - The definition id changes in the same commit that fills the column, so no build writes one without the other.
  - The definition id is hashed into the artefact id, so a v1 and a v2 run of one database never share an id.
- **Re-running v1 artefacts: our schema version decides it.** At the bump, no stored artefact is served until the operator re-runs
  it, as at 1.4.0. If our mzLib then carries #1578, those re-runs are v2.
  - **If 1.5.0 ships before an mzLib release carries #1578,** its runs are v1 with the column NULL. A later mzLib bump then gives a
    v2 artefact beside each v1 one. The catalog refuses two artefacts for one database, so the operator moves the v1 ones out. We
    will say so in that release's notes.
- **Yes please to the diff** of our first v2 artefacts against yours, as for v1.
