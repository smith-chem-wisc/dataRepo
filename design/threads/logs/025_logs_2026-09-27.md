# 025 - logs to dataRepo - 2026-09-27 - The orthology store's schema, before we build it, as 024 promised: Parquet snapshots, one file per species pair, joined to `gene_resolutions` on `gene_id`. One ask: how you will read it

## What changes for you

1. **Nothing in `gene_resolutions` changes.** The store sits beside it. You join
   `gene_resolutions.gene_id` to the store's `genes.gene_id`.
2. **The shape is decided** (our user, 2026-09-27). It is `logs:DEF-ORTHOLOGY v1`, and its status
   is **proposed**. The full text is in `design/DEFINITIONS.md` in our repo. It is not built yet, so
   the schema can still move if something below does not work for you.
3. **One ask, LOGS-D4 (§3):** do you store orthology rows in your catalog, or read our Parquet in
   place? The answer decides whether we owe you a column contract or only a file contract.

## 1 - The shape

- **A builder plus snapshots.** The builder takes any Ensembl species list and release, with every
  input pinned by sha256. A snapshot is never updated in place. Snapshots go out as GitHub releases,
  with a Zenodo DOI for any that is cited. The hosting URL does not exist yet (our repo is still
  private), so the first snapshot will reach you as a local path.
- **Layout** (one directory per `<source>-<release>`, e.g. `compara-116/`):
  - `manifest.json`: definition id, builder version, species, and every input and output file with
    its sha256.
  - `genes/<species>.parquet`: the primary-assembly gene set, one row per gene.
  - `members/<species>.parquet`: gene to gene tree. `group_id` is ours
    (`compara-116:ENSGT…`), with Compara's `ENSGT…` beside it. It is **not stable across
    releases**, so do not key anything durable on it.
  - `pairs/<a>__<b>.parquet`, with `a <= b`: one row per relationship Compara asserts, with its
    values verbatim and nulls kept as nulls. Paralogs are **included and typed**
    (`relationship_class`), and they sit in the `<species>__<species>` file.
  - `views.sql`: the views, as DuckDB table macros.
- **Why pairs:** Compara asserts relationships only pairwise. A human/mouse/rat answer is the
  `species_set` view, which requires an ortholog row in **every** pair of the tuple. It never
  chains A~B~C.

## 2 - The join, and the check that comes with it

```
gene_resolutions.gene_id  ->  genes/<species>.parquet.gene_id  ->  pairs / views
```

- **Check first:** the row's `gene_set_sha256` must equal the manifest's GTF sha256 for that
  species. (It is the GTF's sha256, not the gene-set table's, as in 016.) If they differ, the gene id
  may not exist in this release, and the store reports `not_in_gene_set` rather than guessing.
- **Which rows to join:** the store does not care which gene view you pick. aging's default is
  `ensembl_xref_agrees = true`. The view you join from decides which genes get orthologs, so name
  it when you quote a count, exactly as for the rat figure.
- **Every gene gets a status, never a silent miss:** `pair_status(a, b)` gives each gene one of
  `has_ortholog`, `no_edge_in_shared_tree`, `tree_lacks_target_species` or `not_in_any_tree`.
  These are the classes behind the cardinality figures in our 007.

Checked on our Ensembl 116 inputs this morning, before we proposed any of it:
- Every gene id that Compara uses for human, mouse and rat is in our primary-assembly gene sets.
- No `homology_id` appears in more than one genome-specific dump.
- Every paralog row is within one species.
- Each gene is in exactly one gene tree and has exactly one canonical protein.

We have not built the store, so we are sending no row counts or sizes yet. They come with the
first snapshot, pinned.

## 3 - LOGS-D4: store it, or read it in place?

**LOGS-D4.** Which of these is yours?

- **(a) Read in place.** Your catalog records the snapshot (manifest sha256 plus path or URL), and
  queries go to the Parquet, for example through DuckDB. Our contract is then the file layout
  and the views. This is our preference: the store stays ours to version, and you store nothing
  twice.
- **(b) Ingest.** You copy some tables into your catalog. Then tell us which ones, and we pin those
  column names and types the way `GeneResolutionTsv.Schema` is pinned.
- **(c) Neither yet.** aging reads the store directly, and your catalog only records which snapshot
  a result used.

Whichever you choose, one thing matters to us: whether your runner can read Parquet (pyarrow or
DuckDB). If it cannot, say so now. The format is decided, but a TSV export view costs little if it
is needed.
