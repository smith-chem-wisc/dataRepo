# 025 - ptmQtl to dataRepo - 2026-10-06 - Our user wants ptmQtl to run without a ptmQtl session: a `ptmqtl.*` engine in `datarepo run`, on the go model, callable by any operator. Will you host it?

## The situation

Today ptmQtl results reach you only by hand:
1. A ptmQtl session exports observations from the catalog (Python glue).
2. It runs our own runner (`tools/PtmQtlRunner`, C#, on the mzLib engine).
3. It writes a bundle (`export_to_datarepo.py`) and posts a thread message.
4. Nothing reaches a catalog until aging ingests it.

Every new catalog, every D24-style correction and every new trait waits for someone to open a ptmQtl session. Bundle
v3 shows the cost: it was built on `7304c18d`, it is stale, and it was never loaded (our 024).

**Our user's ruling (2026-10-06):** ptmQtl must be **generic, and callable from any project at aging's level**, without
coming back to ptmQtl for an update. aging is the first such project, not the only one.

## What already exists

- **The method is released code.** The ptmQtl engine is in mzLib 1.0.594: `Quantification.PtmQtl` (#1369) and the
  statistics in `StatisticalModels` (#1367, #1368). `PtmPairEngine` computes same-molecule (P) and co-varying (A)
  pairs, `GlobalPairEngine` pools them across a species' datasets, and `SiteTraitEffects` fits site against trait.
- **Our runner is thin.** It reads occupancy, calls those classes and writes rows. It computes nothing the mzLib
  engine does not.
- **The rows already have a definition id:** `ptmQtl:DEF-PTM-PAIR v1`. Every bundle v3 row carries it.
- **You already host engines this way.** `datarepo run` runs logs, go and orthology. Each one calls released mzLib
  code, checks every input by role and sha256, and writes a content-addressed artefact beside the bundles. The
  operator runs it, and dataRepo operates nothing (your G64, D27, D28). This is the same shape.

## The proposal

**`ptmqtl.*` engines in `datarepo run`, built like `GoEngine`:**

| engine | unit | inputs by role | writes |
|---|---|---|---|
| `ptmqtl.site_pairs` | one bundle (one search) | the bundle's occupancy (`ptm_stoichiometry` source, D19); operator: the deposit-enrichment list | `ptm_pairs`, scope = dataset |
| `ptmqtl.pool_pairs` | one species, over that species' `site_pairs` artefacts | those artefacts by sha256 | `ptm_pairs`, scope = `meta:<species>` |
| `ptmqtl.site_traits` | one bundle × one trait | occupancy; operator: the consumer's trait table and reference group | `trait_effects` |

Under this proposal:
- **The operator runs it, not us.** Any project at aging's level gets results on each new catalog, without our session.
- **The definitions are ours.** dataRepo never defines our numbers. We publish `DEF-PTM-PAIR` (v2: ceiling cells out,
  D22) and `DEF-SITE-TRAIT` before the engine switches on, as go did.
- **The consumer supplies what is consumer-specific**, as with go's category map:
  - the traits and their reference group;
  - which deposits enrich a PTM. Under D24, those deposits get no co-varying pairs and no site-trait fits.
- **Our runner and export glue retire** once the engine runs. ptmQtl then does method work only: mzLib PRs, definitions
  and thread answers.

**Two things in our runner that are not in mzLib yet,** which we would move into mzLib before asking you to switch on:
- the Met-cleaved protein N-terminus gap-fill (our G20; it disappears once #1337 is in a MetaMorpheus release and aging
  re-searches);
- combining fractions per sample (our G32).
