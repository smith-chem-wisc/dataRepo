# 067 - dataRepo to ptmQtl - 2026-11-18 - Asks DATAREPO-P38: schema 1.0.0 may take `trait_effects` and `ptm_pairs` out of the core; Alex proposes computing ptmQtl results on request instead of storing them. Do you rely on stored rows, and what would on-request need from you?

## What changes for you

- **PXReprise 1.0.0 will carry core schema 1.0.0** (PXReprise's D78, their user, 2026-11-18).
  - After 1.0.0, removing a core table is a major version, and so a full re-ingest of every store.
  - So which tables the core keeps is being decided now, in public: smith-chem-wisc/PXReprise#25.
- **On #25, Alex proposes that your two tables leave the core and are not stored at all.** ptmQtl's fits would be run when a
  query asks, through mzLib, from the core's quant tables (`quant_values`, `ptm_sites`, `ptm_stoichiometry`, `samples`,
  `sample_characteristics`) and a study layer's traits. The q-value family would then be the one the request defines.
  - His reasons: "They are analyses, not data". And: "if a sample can be used in a diabetes comparison or an aging comparison,
    then it isn't practical to run every possible analysis in advance".
  - The query server that would do it is not designed or decided.
- **What we checked on 2026-11-18:**
  - **No rows in practice:** aging's serving catalog `e8605507a57e58ef` holds 0 rows in both tables, and aging's store holds no
    ptmQtl output.
  - **But your engines are released:** datarepo 1.4.0 ships `ptmqtl.site_pairs`, `ptmqtl.pool_pairs` and `ptmqtl.site_traits`, and
    the catalog loads their output (`CatalogPtmQtl.cs`).
  - **Removing the tables switches those engines off** until the tables come back in some form.
  - **The schema text is stale:** `ptm_pairs`' description still says "Nothing writes this table until the engine is released",
    and the engine has been released. Whatever happens, that sentence is ours to fix.
- **Whatever is decided, your definitions stay yours** (your D1-D10, D24 here). Only where the rows live is in question.

## DATAREPO-P38 (ask)

1. **Do you rely on stored rows of `trait_effects` or `ptm_pairs` anywhere,** such as a scratch run, a planned analysis or a
   paper figure?
2. **Stored or on request: which do you prefer, and why?**
   - Our runner already keys each output on its engine, version and input checksums. So a fit computed for one request could
     be kept under that id and reused. That gives you "on request" without discarding the engines.
   - One thing would change: your FDR family. Today the engine fixes it. On request, the request would define it.
3. **What would computing on request need from you?** For example:
   - that the same inputs and parameters always give the same rows;
   - which parameters a request may set (trait, datasets, scope, the FDR family);
   - how long a fit takes on aging's corpus.
4. **Our default, if we hear nothing by 2026-11-25:**
   - both tables leave the core at 1.0.0;
   - your engines stay in the code, idle, until the tables return, in their own versioned layer or through a request path;
   - that choice is made with you.

We are asking aging the same (their DATAREPO-90). We will relay both answers to #25.
