## DATAREPO-P35: the proposed shape

### Where the values come from

- **A PRIDE record describes the deposit, not our search, and PRIDE edits it after deposit** (a paper is added when it
  is published). Today 22 of 193 deposits list no paper, and 31 of 175 papers have PubMed id 0.
- **So it stays out of the bundle.** Inside a bundle, a paper PRIDE adds later would move the bundle id while every
  search row stays the same. A new bundle table is also a schema bump, which re-ingests the whole store.
- **Instead:**
  - the operator (PXReprise, for aging) fetches the records with a datarepo command, through mzLib's
    `PrideArchiveClient.TryGetProjectAsync`;
  - each record is kept in the store with its sha256, its fetch time and the mzLib version;
  - `build` reads the newest record per accession;
  - the catalog id covers each record's sha256, so a refetch that changes a row gives a new catalog id.
- mzLib returns a `PrideProject`, not PRIDE's response body, so we store the fields as mzLib reads them.

### The tables (names provisional)

**Key:** `accession`, the bare PXD. A split deposit's datasets (`<accession>-<group>`) share one record. Join with
`split_part(datasets.dataset_id, '-', 1) = accession`.

1. **`deposit_records`**, one row per accession:
   - `accession` and `archive` (`PRIDE`);
   - `found`: false when PRIDE has no record for the accession, which then has no rows in the other two tables;
   - `fetched_utc`, `record_sha256`, `mzlib_version`.
2. **`deposit_contacts`**, one row per person per role:
   - `accession`;
   - `role`: `lab_head` (PRIDE's `labPIs`) or `submitter` (`submitters`);
   - `ordinal`: the place in PRIDE's list, which is not a rank;
   - `name`, `title`, `first_name`, `last_name`, `affiliation`, `country`, `orcid`, `pride_contact_id`: as PRIDE wrote
     them, untrimmed. PRIDE's empty string becomes NULL;
   - **e-mail is left out on purpose.** It is personal contact data, and a lab rule does not need it.
3. **`deposit_references`**, one row per paper:
   - `accession` and `ordinal`;
   - `reference_line`: the citation as PRIDE formats it;
   - `pubmed_id`: NULL where PRIDE writes 0;
   - `doi`: NULL where empty.
   - The project's own DOI (`10.6019/PXD...`) names the deposit, not a paper, so it is not in this table.

## Same raw files under two accessions: what the catalog knows

- **`runs.sha256` is the sha256 of every searched raw file:** all 4,847 runs in `abfeaa1bf5c73d4d`, all `.raw`.
  `runs.pride_checksum_sha1` is PRIDE's own checksum, present for 2,814 of them.
- **No file name is shared by two accessions. By sha256, three files are:**
  - PXD033430's `Control-1.raw`, `Control-2.raw` and `Control-3.raw` are PXD057544's `Con1_Lum_20mar1101.raw`,
    `Con2_Lum_20mar1102.raw` and `Con3_Lum_20mar1103.raw`, byte for byte. That is 3 of each deposit's 9 runs. Both
    deposits have Dasarathy as lab head and the same submitter.
  - PRIDE publishes no checksum for PXD057544's files, so only our sha256 sees this. A test on names or on PRIDE's
    checksums misses it.
- **Within one deposit:** PXD006815's `20170508_QEp7_JRW_SA_T_Z73a.raw` and `20170508_QEp7_JRW_SA_T_Z74.raw` are
  identical (our sha256 and PRIDE's sha1 agree). aging's group map for this deposit
  (`design/source/2026-10-21_PXD006815-group-map`) puts them in two experiments, A5 (animal Z73) and A6 (animal Z74).
  aging has not been told yet.
- **Limits:**
  - only searched runs are in `runs`, so a deposited file that nobody searched is not compared;
  - only deposits in this catalog are compared;
  - file sizes are not stored.
- **The query:**

  ```sql
  SELECT sha256, list(DISTINCT dataset_id) AS datasets, list(file_name) AS files
  FROM runs GROUP BY sha256 HAVING count(*) > 1;
  ```
