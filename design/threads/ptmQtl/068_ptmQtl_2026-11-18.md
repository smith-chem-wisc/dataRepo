## 2 - P38 part 2: stored, and why

- **Pairs take no trait.** A deposit and a method version give one answer. Alex's point ("it isn't practical to run
  every possible analysis in advance") is right for site-trait rows, where the requester chooses the trait. It does
  not apply to pairs, where there is only one analysis to run.
- **Pooling needs every deposit's tests, every time.** A pooled network for a species combines every deposit's
  tested pairs, not only the significant ones (Stouffer's Z). Recomputing them for each request repeats the same
  work: 37 minutes on our corpus today (section 3).
- **A result someone cites must be the same result next year.** Recomputing on request gives the same rows only if
  the inputs, the parameters and the mzLib version are all unchanged. Storing the rows with that record (section 4)
  makes this checkable. Recomputing without storing makes it a hope.
- **Site-trait rows on request are fine,** provided they are stored as computed. The trait is the consumer's (D25),
  and so is the family of tests corrected together. A request that defines its family gets a recorded family.

## 3 - P38 part 3: what computing on request would cost, for a repo larger than aging's

### Measured today, on one machine (64 logical cores)

| what | size | time |
|---|---|---|
| v5 pairs, whole corpus, one deposit after another, then pooled per species (`results/pairs_6a81_v5`, catalog `6a81a1a2`) | 121 deposits, 2,741 runs, 227,700 sites, 40,152 same-molecule pairs, **60,337,397 co-varying tests**, 19,004 at q <= 0.1 | **37 min 24 s** |
| v5 pairs, largest deposit alone (PXD008934) | 254 runs, 7,744 sites, 5,299,638 tests | **36 s** |
| v5 pairs, median deposit alone (PXD044773) | 1,559 sites, 49,375 tests | **4 s** |
| depth null (D78), 3 shuffles per deposit, whole corpus | 3x the co-varying tests | about 6 min, all 64 cores |
| site-trait, made-up two-group trait, median deposit (PXD044773), without bounds | 21 runs, 1,559 sites in, 104 fitted | **0.1 s**, all 64 cores |
| site-trait, the same, with bounds as counts given run depth (mzLib 1.0.598) | 21 runs, 1,559 sites in, 160 fitted (430 "mostly one bound") | **185 s**, all 64 cores |
| site-trait, largest deposit (PXD008934, 254 runs), with bounds | 254 runs, 7,744 sites in | **more than 32 min**, all 64 cores (about 24,000 CPU-seconds), and still running when this was sent |

- Both single-deposit pair runs reproduced v5's files byte for byte today.
- The site-trait rows are timings only: the trait is made up (runs paired into pseudo-animals, alternating groups).

### How the cost grows

- **Across deposits it grows linearly, and deposits are independent.** They can run side by side. With one deposit
  per core, the corpus's wall time is set by its largest deposit: about 36 s today. That figure is an estimate; we
  ran the deposits one after another.
- **Within a deposit it grows with the square of the sites that enter.** The number of tests is s(s - 1)/2 for s
  sites, so a deposit with twice the sites costs four times as much. Deeper searches, more PTM classes, and bounds
  (which let more sites enter) all raise s. PXD008934's 5.3 M tests mean about 3,260 sites entered.
- **Pooling grows with the number of tests stored.** A repo ten times aging's, with deposits like ours, holds about
  600 M co-varying tests. Our runner keeps every test in memory until it pools, which will not scale that far. A
  build at that size should store each deposit's tests and pool them per species, by pair key, in a stream.
- **Site-trait grows with sites x traits x deposits,** and each site is an iterative fit.
  - Without bounds it is cheap: 0.1 s for the median deposit.
  - With bounds as counts it is about 1,800 times slower: 185 s for the same deposit, on 64 cores.
  - At the median deposit's cost, one trait over our 121 deposits would take about 6 hours on this machine, and over
    a repo ten times aging's about 60 hours. That is arithmetic, not a measurement. The largest deposit had run for more than 32 minutes and had not finished when this was sent. We will send its time.
  - So site-trait with bounds, our end state, is the step that is not rapid. It is a job whose rows are stored, not
    something to run while a requester waits.
- **So "rapidly" means:**
  - pairs computed once per deposit and method version, then read;
  - pooled rows built at each publish from stored per-deposit tests;
  - site-trait fits per trait, deposit by deposit, then stored.

  A request then reads rows and computes only what is new to it: a new trait, or a new family.

### What a stored per-deposit result must hold for pooling

- Our per-deposit files hold only the significant co-varying pairs and every same-molecule pair (419 MB of TSV for
  121 deposits). Pooling needs every tested pair. There are two ways to provide that:
  - **(a)** store every tested pair per deposit (site a, site b, rho, p, n): 60.3 M rows today;
  - **(b)** store occupancy only, and recompute each deposit's tests at every publish, side by side (about the largest
    deposit's time on enough cores).
- Either way works for us, provided the pooled rows carry their record. Which one your engines do today, we don't know.

### What a request may set, and what it may not

- **A site-trait request may set:**
  - the trait (its id and values per run);
  - which runs or samples are used;
  - covariates;
  - the replicate grouping (the animal is the replicate, never the run);
  - the family of tests corrected together.
- **A pairs request may set** which deposits to pool. A pooled family over its own deposits is then the request's,
  and recorded.
- **No request may set the definitions.** This covers:
  - which runs (whole-proteome only: S3b and D24, so no occupancy from PTM pulldowns);
  - which sites (S2 and its exclusions);
  - the 70 % entry rule;
  - how bounds enter;
  - MinRuns and MinReplicates.

  A change to any of these is a new definition version, not a parameter.
- **One trap for site-trait on request.** With bounds as counts, the detection link and the borrowed run scatter are
  fitted from the sites in the call. A request for a subset of a deposit's sites would therefore change each site's
  result, not only its q. Our definition already makes the link per deposit (S1). So:
  - fit every site of the deposit for the trait, store the rows, and let a request select rows and its own family;
  - or store the deposit's link and pass it in (`SiteTraitOptions.DetectionLink`).

## 4 - What must be stored to compute a result again

With every stored result (one per deposit, and one per pooled scope):

- **Definitions:** the definition id and version (`ptmQtl:DEF-PTM-PAIR`, `ptmQtl:DEF-SITE-TRAIT`), and the versions of
  the lists it applies: the capture list (`results/ptm_enriched_v4`), and the S2c, S2d and S2e exclusions.
- **Code:** the exact mzLib version, your engine's version and commit, and the .NET runtime.
- **Inputs, by content checksum, not by bundle id alone.** Your bundle ids move at 1.5.0. Per deposit, that means:
  - the occupancy rows read (`ptm_stoichiometry`);
  - the observations (for same-molecule pairs, and the coverage that makes covered-zeros);
  - each run's depth (target PSMs under S7's rule);
  - the trait table, for site-trait rows.
- **Parameters:** everything the call passes. For pairs: `aQ` 0.1, the 0.7 entry fraction, bounds, run depth. For
  site-trait: the scale, `BoundCells`, `MinRuns`, `MinReplicates`, the coefficients tested, the link used, and the
  family.
- **Seeds:** the depth null shuffles from a seed that is a fixed function of deposit and shuffle number. .NET's
  `HashCode.Combine` must never make it: it changes with every process.
- **Outputs:** a checksum, and counts by status (tested; "not tested: both sites mostly one bound", D43; "not fitted",
  D48).
- **The check:** recomputing from the record gives byte-identical rows. We did this today for two deposits on one
  mzLib version. A different mzLib version can move the last digits of an iterative fit (REML stops at a tolerance),
  so the version belongs in the record.

Your runner already keys each output on engine, version and input checksums. The definition versions, the
parameters, the trait table and the family are what this list adds.

## 5 - v5, our reported method (D80)

**Co-varying pairs** (DEFINITIONS S1, D37 and D40):

- **Bounds:** a run where a site was seen in only one form enters as a bound, at its rank:
  - a covered-zero or floor is tied lowest;
  - a ceiling, or a count-only cell where only the modified form was seen, is tied highest.

  Our runner's flags are `--include-bounds --run-depth`, on mzLib 1.0.596 or later.
- **Depth:** the correlation is partial, given each run's depth (log2 target PSMs, S7's rule;
  `tools/export_depth.py`).
- **No run-level variant with bounds (D77).** With bounds, the median run level is a constant or marks one run, so the
  runner refuses the combination.
- **Two steps around the mzLib calls:**
  - a covered-zero is the engine's coverage (unique-protein peptidoforms) for a catalog site in a run where the
    catalog has no cell;
  - a count-only cell takes the engine's peptidoform counts for its run.

  Both apply only to searches up to MetaMorpheus 1.1.12. Version 1.1.13 writes its own 0/N cells, and the two are
  never mixed.
- **A deposit can be labelled depth-like (D78).** This happens when shuffling each site's cells among runs of similar
  depth gives at least 10 % as many calls as the real data. The label is shown, and the deposit is never dropped. On
  6a81 the label marks 32 deposits, holding 603 of 19,004 pairs. The shuffle is not in mzLib, so your engine cannot
  make the label yet.
- **These rows need a new definition version.** `DEF-PTM-PAIR v2`'s type A still describes the October rule (ceilings
  out). We will write v3 into our DEFINITIONS before your engines move. With it comes a reference case v3 (v5's rows
  on a small fixture), so your engine can be checked against it as it was against v1 and v2.

**Site-trait:** the method with bounds is decided (S1: D39, D44-D49) and released in mzLib 1.0.598. We have not yet
run it on our corpus, and will tell you when it is our reported method. Until then, `DEF-SITE-TRAIT v2` (log2 odds,
no bounds) is the current definition.

**Results:** `results/pairs_6a81_v5` (README there): 19,004 co-varying pairs at q <= 0.1 in 73 deposits.
