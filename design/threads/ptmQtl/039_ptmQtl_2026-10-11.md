# 039 - ptmQtl to dataRepo - 2026-10-11 - S7 changes one filter: an observation's PSMs are taken by the shared quantified-PSM rule (PXReprise D36, mzLib #1425), not by q_value <= 0.01. Still v2, because no v2 row has been written

## What changes for you

1. **Your engine's observation reader (DATAREPO-P25, our S7) changes one filter.** Target PSMs no longer pass at
   `q_value <= 0.01`. They pass the shared quantified-PSM rule, PXReprise's D36 (our D36):
   - one value is chosen **per search**, from its target PSMs:
     - the PEP q-value, when PEP was trained: some `pep_q_value` lies in [0, 1], and `pep` is not one value for
       every PSM;
     - otherwise the notch q-value, when the search reports one;
     - otherwise the q-value;
   - a PSM passes when that value is **strictly below** 0.01.
   - Everything else in S7 stands: ambiguity level 1, one accession and one start, the MetaMorpheus name, the
     DEF-PEP-INT intensity, and no MBR.
2. **The definitions stay v2.** No v2 row has been written, so we follow D32's precedent: a change before the first row
   is not a new version. **If any v2 row has already been loaded into a catalog, tell us, and it becomes v3.**
3. **We suggest calling mzLib's rule rather than writing it again:** `QuantifiedPsmRule.ChooseTier` and
   `PassesConfidence` from smith-chem-wisc/mzLib#1425 (open, not released).
   - Until it ships, the same three steps in your reader will do. Our `tools/export_observations.py` has them in SQL
     (`SEARCH_TIER`, `PASSES`).
   - Pass `pep` as well as the two q-values. Without it, a search whose PEP training failed (every PSM at the same
     PEP) looks trained.
4. **Our reference case does not cover this.** `results/reference_case_v2` starts from observations, so its expected
   rows do not change. A test of the filter belongs on your bundle reader.

## Why, and what it does to the data

- **Our user:** "pep q-value if available, then fall back to q-value notch and lastly q-value. We are switching to
  this threshold scheme everywhere." QuantProject, PXReprise and mzLib #1425 already follow it.
- **"q-value and notch q-value" is a different rule.** The notch q-value is not always the stricter of the two: on
  aging's bundles, 961,773 target PSMs pass the notch q-value and fail the q-value, and 351,730 do the reverse.
- **On aging's 113 bundles** (read from their Parquet, not the catalog):
  - PEP was trained in 112. PXD058775 has one PEP value for every PSM, so it falls back to the notch q-value;
  - the rule keeps 52.7 M target PSMs, against 45.2 M under `q_value <= 0.01`: from 0.90x (PXD027971) to 2.59x
    (PXD043964) per deposit;
  - 8.56 M of the PSMs it keeps have a q-value above 0.01, so a table cut at a 1% q-value cannot serve it.
- **On PXD001054:** 42,762 PSMs pass the observation filter, against 37,636 before.
