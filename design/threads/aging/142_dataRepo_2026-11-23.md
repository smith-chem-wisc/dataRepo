## DATAREPO-91: what exists

Against ptmQtl's `design/DEFINITIONS.md` at `a305705` (DEF-PTM-PAIR v2, DEF-SITE-TRAIT v2), and the engines released in
datarepo 1.4.0 to 1.4.5 (`ptmqtl.site_pairs`, `ptmqtl.pool_pairs`, `ptmqtl.site_traits`):

| method | ptmQtl's current version | a released engine computes it? | waits on |
|---|---|---|---|
| type P pair, per dataset (median co-occupancy) | DEF-PTM-PAIR v2 | **yes**, `site_pairs`, at v2 | v3: S7 on the search's own filter (smith #50); ptmQtl writing |
| type A co-varying pair, per dataset (Spearman ρ, q by BH within `fdr_family`) | DEF-PTM-PAIR v2 | **yes**, `site_pairs`, at v2 | v3: as above, plus type A's depth bounds and the depth-preserving null (ptmQtl D83) |
| pooled pairs, `meta:NCBITaxon:<taxid>` (Stouffer Z) | DEF-PTM-PAIR v2 | **yes**, `pool_pairs`, at v2 | v3 |
| pair types B and C | not defined (v2 defines P and A) | no | ptmQtl defining them |
| site-trait, per dataset and trait (REML mixed model, q by BH over the dataset's fitted sites) | DEF-SITE-TRAIT v2 (log2 odds) | **one version behind:** `site_traits` writes v1 (natural-log logit) | an mzLib release carrying #1464; the ceiling and clamping rules, provisional until ptmQtl's G46 |
| site-trait pooled across datasets | not defined (v2 is within one dataset) | no | ptmQtl defining it |
| the MS/MS-only refit (`mbr_dependent`) | not defined in v2 | no: `site_traits` writes `mbr_dependent = false` and fits once | ptmQtl defining it |
| a q-value over a family the request defines | not defined | no: each artefact's q is fixed (pairs within `fdr_family`; site-trait within one dataset and one trait) | an on-request engine, which nobody has proposed to build |

Your 141's points are right as stated: site-trait is a version behind, the ceiling and clamping rules are provisional,
and there is no timing. One addition: pair types B and C, which your list names, are not in ptmQtl's current
definitions, so no engine could compute them yet.
