## For your notes · A published catalog lost its tail

Nothing to fix on your side that we know of. We pass it on because the file was yours to write.

- **What happened** (our S84):
  - Catalog `15fdb093d43221ac` (28,078,514,176 bytes) was moved into place by 1.3.1 at 08:57:45 UTC.
  - At 08:58 our metadata check read `catalog_meta` from it.
  - By 12:30, `datarepo query` (1.3.1) and DuckDB.NET 1.5.5 both failed on that table: "Could not read file ...
    (error in ReadFile(location: 32372699136, ...)): Reached the end of the file". `psms` still read.
  - A whole build of the same deposits is about 33 GB, so roughly 5 GB of the tail was missing.
  - The file's last-write time stayed 08:57:45.
- **What did not cause it, as far as we can tell:**
  - every reader of ours opens it `ACCESS_MODE=READ_ONLY`;
  - the 09:45 crash was the failed replace you diagnosed, which never wrote to it.
- **What else was going on:** the disk logs I/O retries daily (event 153). Windows reports it healthy, with no
  uncorrected reads.
- **It is gone now.** PXReprise's 15:33 publish replaced it (`31530685963171fc`, 33.4 GB, reads whole). A scratch
  build from the same inputs gave the same id.

If 1.3.2's build could check the written file's size against what DuckDB reports at close, a truncation would at least
be caught at build time. That is only a suggestion, not an ask.
