## DATAREPO-78: a 1.3.0 MCP server does block the replace

- **Your 098 measured a delete, not a replace.** On Windows, a file another process holds open can be deleted when the
  holder allows it, and DuckDB allows it, even read-only. But the file cannot be replaced.
- **Measured here** with a read-only DuckDB reader on a catalog:
  - replace (MoveFileEx with REPLACE_EXISTING): "Access is denied" (WinError 5);
  - delete: works;
  - rename the new file into the freed name: works;
  - the reader keeps answering from the old file.
- **Reproduced with the released 1.3.1 binary.** We ran `datarepo mcp` on the tutorial catalog with one `describe`,
  then `build --overwrite`.
  - The build exited 0xE0434352 at `Catalog.cs:1343` <- `CatalogCommands.cs:89` <- `:53`, the stack of both batch
    crashes.
  - The staged file was left behind.
  - With the server stopped, the same rebuild succeeds.
- **Why 0.32.0's builds worked under the Python servers.** `catalog.py` deleted the old catalog first and then renamed
  (`out.unlink(); staging.replace(out)`). The C# port replaces in one step. Our parity tests compared rows, so they
  never saw this.
- **Our project's own entry** (frozen Python, `python -m datarepo.cli mcp`) no longer starts here: it failed to connect
  in today's session, so it holds nothing. We will point it at the 1.3.2 binary.
- **Who held the catalog at the two batch crashes is still unknown.** No Claude session in aging or dataRepo was active
  at either time, by their transcripts. With 1.3.2, a holder that still blocks the build is named in the refusal,
  item (b) below.

## DATAREPO-81, item by item

| your item | 1.3.2 |
|---|---|
| (a) retry the move | **Done, and the common case no longer waits.** A DuckDB reader (an MCP server, a script) does not block at all: the old catalog is deleted under it and the new one moved in. A holder that refuses deletion as well (antivirus, a backup, a copy) gets retries with a growing wait, for up to 10 minutes, your figure. |
| (b) name the holder | **Done.** On a refusal, Windows' Restart Manager (`RmGetList`) names each process holding the catalog or the staged file: "Held by <name> (pid N)". |
| (c) the staged file | **Done.** A refusal deletes it and says so. In one case it is kept: when the old catalog has already been deleted and the new one still cannot be moved in. The message then says to rename it into place. **Not done:** removing old `.building` files when a build starts. On Windows a concurrent build's file can be deleted while it is being written, so one build would destroy another's work. A refusal no longer leaves a file behind. |
| (d) the message on one line | **Done.** A refusal is one line on stderr, `datarepo: <catalog> could not be replaced ...`, with no stack. Any other unexpected error prints its stack and then, as the last line, `datarepo <command>: unexpected <type>: <message>`, and exits 70. A log that keeps the tail now keeps the message. |
