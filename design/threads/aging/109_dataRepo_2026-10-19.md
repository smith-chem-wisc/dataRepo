## DATAREPO-82: the checks as we will build them

Each refuses the delivery:
- **`role`** is required, one of `condition` or `stratum`.
- **A condition** has at least one level with `is_reference = true` and at least one other level, within its dataset.
- **A stratum** has at least two levels, and `is_reference` is empty on every one of its rows.
- **`level` never holds a reserved word** (`not applicable`, `not available` and the rest of the list
  `curated_sample_characteristics` uses). A run that the factor does not concern has no row for it.
- Unchanged from our 106: every run in `curated_design_factors` is in `curated_run_design`; every run of one sample
  carries the same factor rows; every `run_id` is a run the catalog holds; no level is both reference and not.

## Your 107: what cut the catalog

**The facts.** Your failing read and the file's length are both on DuckDB's block grid, or not:
- The read that failed was at 32,372,699,136, which is exactly block 123,492 (12,288 + 123,492 x 262,144). Your
  08:58 read of `catalog_meta` reached that block, so at 08:58 the file was at least 32.4 GB long. By 12:30 it was
  28,078,514,176.
- A whole DuckDB 1.5 file is exactly 12,288 + `total_blocks` x 262,144 bytes. We measured that today, to the byte, on
  a fresh file and on your current 62.4 GiB catalog. DuckDB writes, and trims, whole blocks only.
- 28,078,514,176 is **4,096 bytes short of that grid**. So DuckDB did not cut it. Something cut it at a 4 KiB
  boundary, which is an NTFS cluster.
- **Nothing in datarepo opens a published catalog for writing.** The one read-write open is the staged file, closed
  before the move (`Catalog.cs:1297`). The MCP server, `site` and every reader open it read-only. The 1.3.1 replace
  that failed at 09:45 is a rename on the same volume, and a failed rename leaves the destination untouched.

**So the likeliest cause is the file system or the disk** (your daily event 153 retries). Two things worth doing on
that machine:
- read the System log from 08:58 to 12:30 for Ntfs events (55, 98, 140) and disk events (7, 51, 153);
- run `chkdsk F: /scan`, which runs online and only reports or queues repairs.

It is PXReprise's machine, so we are telling them too.

**What 1.3.3 adds.**
- `build` checks the written file's length against its header before moving it into place.
- The MCP server checks it whenever it opens a catalog, and refuses a short one: `refusing to serve a damaged catalog:
  ... N bytes short of the M its own header describes`.
- Neither would have stopped your 08:57 publish, because the file was whole then. A server opened after the cut would
  have refused the catalog, instead of answering from its head until a query reached the tail.
- A test reproduces your symptom exactly. A file cut short opens, a table near its head reads, and a table at its tail
  fails with "Reached the end of the file".

## G101: two keratins' sites are written twice

- `ptm_sites` places a site against every sequence its accession has in the searched databases. MetaMorpheus's
  contaminant panel carries older versions of two human keratins:
  - O76011: 436 residues, against the proteome's 394;
  - P19013: 534 residues, against 520.
- So each modification on them is written twice, 42 or 14 residues apart, with the same `n_psms`. Example: PXD022180,
  `Carbamidomethyl on C` at O76011 351 and 393.
- Measured on 2026-10-11: 411 sites in 25 of 113 bundles.
- **Until 1.4.0:** leave out O76011 and P19013 from any site count, or count one row per (accession, modification,
  `n_psms`).
- **At 1.4.0:** a site whose accession has two sequences gets no window and is counted (ptmQtl's P31). We will decide
  there whether it is written once or not at all.
