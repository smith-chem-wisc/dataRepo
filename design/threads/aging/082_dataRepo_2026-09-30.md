## REQ-DATAREPO-7: cause, checked in mzLib's source

Your guess about suffix-strip order was close, but the name was already changed before it reached us.
mzLib's `SpectrumMatchFromTsv` (mzLib `33f9e618`) runs `Replace(ext, "")` for each of `.raw`, `.mzML`,
`.mgf`, `.d`, `ms1.msalign` and `ms2.msalign`, case-insensitively and **anywhere in `File Name`**, not
only at the end. So pyMzLib hands us `QEX03_AM_230117_CW10_065.thermo-calib` for your
`QEX03_AM_230117_CW10_065.raw.thermo-calib`.

The fix: `usi.RunNameMap` now also compares each deposited name as mzLib would report it
(`usi.mzlib_tsv_file_name`). It uses that comparison only when it is unambiguous. If two deposited runs
come out of that rule with the same name, neither is matched, because picking one would put PSMs on the
wrong run.

**Scratch ingest of your real output.** This used junctions to your run folder, `db` and
`mm_settings/1.1.11`, a scratch store, and wrote nothing under `F:/aging_data`:
- bundle `e982a3dfb717d4ea`;
- 1,550,591 PSMs on all 24 runs, `run_id` like `PXD075372:QEX03_AM_230117_CW10_065.raw.thermo`, and
  every PSM has a USI;
- `count_mismatch` on `psms_target_1pct`: 1,111,523 against your 1,112,70x (0.1%). This is the known
  notch-ambiguity predicate, not lost runs. The q-value-only count is 1,158,362, and yours lies between
  the two.

Worth knowing on your side: `.d` is on mzLib's list too, so any stem containing `.d` (for example
`run.day2`) is changed the same way. The fix covers that as well.
