# 112 - dataRepo to aging - 2026-10-19 - datarepo 1.3.5 builds your catalog in about 8 minutes as a 300 MB folder, against 1 to 3 hours and 62 GiB. How to switch your publish script and MCP entry, in seven steps

## What changes for you

1. **datarepo 1.3.5 is published:** https://github.com/smith-chem-wisc/dataRepo/releases/tag/v1.3.5, tag `v1.3.5` on `e1525b3`. It includes 1.3.3 and 1.3.4. No re-ingest:
   every bundle keeps its id.
2. **`build --out <folder>` writes a catalog folder** (our D48 step 1, PXReprise's public-data contract):
   - the bundle and engine tables are views over the store's Parquet, so a build copies no rows;
   - each build writes a new `catalog-<catalog id>.duckdb` and then a `latest.json` naming it. No file a reader holds is
     ever replaced, so the MCP server and your scripts keep working through a publish.
3. **Measured on your store,** pinned to your serving catalog `296829073a04b833`'s 169 bundles. The build ran in
   scratch and read your store only.

   | | today | folder |
   |---|---|---|
   | build | 1 to 3 hours | **8.4 min** |
   | catalog file | 62.4 GiB | **298 MB** |
   | `mcp --check` | | 0.6 s |

   - **All 47 tables and views both catalogs hold have the same rows:** counts, plus checksums for every table under
     10M rows.
   - **Two checksums differed, both explained.** PXD007035's manifest notes changed after your 13:20 build. And
     `ptm_sites_by_chemistry`'s name lists have no fixed order; they are equal once sorted.
   - **Your site, regenerated from it with your options, is byte-identical,** with two exceptions:
     - 22 dataset pages swap two findings that share a code. 1.3.5 orders them by `finding_id`, because views do not
       keep insertion order. This happens once;
     - `index.html` differs only because your publish renders the summary into the about page.
4. **`--out <name>.duckdb` still builds one file,** exactly as before. Switching is your choice. We recommend it,
   because it ends the publish time-outs.

## The switch, in order

1. **Install 1.3.5** beside 1.3.2, as PXReprise installs releases: `F:\aging_batch\datarepo-1.3.5\`. PXReprise swaps the
   batch's pin in the same restart (our 048 to them).
2. **Rewrite your study bundle with 1.3.5,** before its first `build`:
   - the aging layer is 0.6.0 since 1.3.4, and the build refuses your current `dd044f2ed9d8ec48` (0.5.0);
   - add `curated_run_design` and `curated_design_factors` to the same delivery YAML (our 111).
3. **In `publish_catalog_and_site.ps1`:**
   - `$DataRepo = 'F:\aging_batch\datarepo-1.3.5\datarepo\datarepo.exe'`;
   - `$Catalog = 'F:\aging_data\repo\catalogs'`, a folder (`build` creates it);
   - the build line becomes
     `& $DataRepo build $Manifest @Accessions --latest @studyArgs --out $Catalog --keep 5`.
     **Drop `--overwrite`:** in a folder an unchanged build writes nothing and points `latest.json` at the existing
     file again, and any change to the content moves the catalog id;
   - after the build, resolve the current file for your own tools, which open one `.duckdb` file:
     `$CatalogFile = Join-Path $Catalog ((Get-Content "$Catalog\latest.json" -Raw | ConvertFrom-Json).catalog)`.
     Pass `$CatalogFile` to `metadata_coverage.cs` and to `publish_tools.cs summary`. `datarepo site` takes the folder
     itself, so `$Catalog` can stay there.
4. **Two blocks can go:**
   - **the staged-file clean-up:** 1.3.3 and later remove a dead build's staged file themselves. In a folder the staged
     names are `.catalog-<id>.duckdb.<id>.building`, which your pattern would not match anyway;
   - **the disk check sized from the 62 GB file:** `(Get-Item $Catalog).Length` of a folder is not the catalog's size,
     and a folder build needs well under 1 GB.

   Keep your "a build is already running" check.
5. **The MCP note after the build changes.** A running server keeps the catalog it opened, as now. Each answer now says,
   in `catalog_file_changed`, that a newer catalog was published; reconnecting serves it.
6. **Repoint your MCP entry at the folder:** `datarepo mcp --catalog F:\aging_data\repo\catalogs --install --force`, with
   the 1.3.5 binary. `datarepo mcp --catalog F:\aging_data\repo\catalogs --check` should then print the new catalog id.
7. **Delete `F:\aging_data\repo\catalog.duckdb` once you are satisfied.** That frees 62 GB. Nothing reads it after the
   switch.

## What a reader sees

- **The same tables, columns and rows.** `catalog_meta` gains three columns:
  - `release_id`, the data: the schema, bundles, study deliveries and engine artefacts;
  - `layout`, `views` here;
  - `data_root`, the store the views read.
- **The views read the store where the build found it,** `F:/aging_data/repo/store/`. If the store moves, rebuild.
- **The MCP sandbox for a folder allows the store and nothing else.** A file outside it, a `..` escape, `ATTACH` and
  `SET` are refused.
