## 089: `excluded_runs` holds searched runs only

**A run that was never searched is already recorded:** its bundle carries an `excluded_from_search` finding, one
per file, with the reason from the search's provenance. So 1.1.0 refuses it in `excluded_runs`: `datarepo
manifest` exits 1 and `build` fails, because there is nothing in the bundle to exclude.

**List only runs that were searched and then excluded:** PXD013240 `VM13`, PXD007999 `PH_F3`, PXD012753 `VM_17`
and `VM_18`. Leave your four Jarome runs and PXD034059's out. The form, in the dataset's manifest entry:

```yaml
    excluded_runs:
      VM_17: "<your reason, verbatim from DECISIONS.md>"
      VM_18: "<...>"
```

Run names are the deposited file names without the extension, as for `run_enrichment`. `datarepo manifest` checks
every name against the runs.

## 088: `dataset_candidates` is yours to fill

**Who and how.** The schema names you as its producer. 1.1.0 reads it at build from a TSV that a new top-level
manifest key names:

```yaml
candidates: candidates.tsv        # relative to the manifest's folder, or absolute
```

**The file:**
- UTF-8, tab-separated, header row required. Cells are read exactly as written, with no quoting.
- Columns, in any order:
  - `census_version`, `accession` and `included` are required on every row;
  - `exclusion_reason` and `definition_id` are optional, and an empty cell means none.
- `included` is `true` or `false`. `accession` matches `PXD`, `MSV`, `JPST` or `IPX` followed by digits. An
  accession listed twice is refused.

```
census_version	accession	included	exclusion_reason	definition_id
2026-10-05	PXD036557	true		DEF-AGING-SCREEN
2026-10-05	PXD000002	false	spectra gate: not HCD Orbitrap	DEF-AGING-SCREEN
```

**What the build does with it:**
- hashes the file into `catalog_id`, so an edited census moves the id;
- names any `included` accession it holds no dataset for, and any catalog dataset the census does not include
  (`catalog_checks`, kind `census`);
- `datarepo manifest` checks the file, and exits 1 on a malformed one.

**The `definition_id` above is an example, not a rule.** The gate's definition is yours to name.

## DATAREPO-74 (ask): dataset-level restrictions, a proposal for you to rule on (087)

PXD012754's "never for protein statistics" is about USES of a whole dataset, not about runs. So it should not go in
`excluded_runs`: a run-level filter would then look complete when it is not. We propose:

```yaml
    restrictions:
      protein_statistics: "<reason>"
```

- **The keys come from a short fixed list you own.** We would start with `protein_statistics`, `quantitation`,
  `age_analysis` and `any_analysis`, and add a key whenever you ask. A free-text key cannot be filtered on, which
  is the reason to take this out of `notes`.
- **How it is served:** read at build like `excluded_runs`, into a `dataset_restrictions` table, hashed into the
  catalog id. No re-ingest and no schema change.
- **Where an agent sees it:** on `dataset_overview` too. An agent reading a dataset's numbers then meets the
  restriction without having to know the table exists (our D19: a tool has to be chosen; a field in the answer
  cannot be skipped).

**Please say yes, or change the keys or the shape.** Until then PXD012754's restriction stays in `notes`, which
1.1.0 serves in `dataset_annotations`.
