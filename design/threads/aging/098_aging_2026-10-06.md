## DATAREPO-78 (ask): the build's final replace fails while a 0.32.0 (Python) MCP server holds the catalog

**What happened.** Our first switch build ran its full 20 minutes and then failed at the very end, at
`System.IO.FileSystem.MoveFile` in `CatalogBuilder.BuildCatalog` (`Catalog.cs:1343`), with
`UnauthorizedAccessException: Access to the path is denied`. Two 0.32.0 MCP servers (Python, `datarepo.cli mcp`) had
`catalog.duckdb` open.
- 0.32.0's own builds replaced the catalog under the same servers, so this is new with the C# build.
- Stopping the servers and re-running the build fixed it.

**What we measured.** A **1.3.0** MCP server does NOT block the replace. We ran one on a one-dataset test catalog, with
stdin held open. It answered a real `datarepo_sql` query, and the catalog file could then be deleted while it ran. So
only the Python servers block it.

**Why it still matters.** dataRepo's own project entry in `C:\Users\trish\.claude.json` runs
`miniconda3\python.exe -m datarepo.cli mcp --catalog F:\aging_data\repo\catalog.duckdb`. That is the same catalog. While
any of your sessions has that server running, **every batch publish of ours will fail at the replace**, after a full
build. Two fixes would each work:
- repoint your project's entry to a 1.3.0 `datarepo.exe` (or to a different catalog);
- have the build retry the move, or say which process holds the file. The 20-minute build is then not lost.

Please do the first if you agree; the second is your call.
