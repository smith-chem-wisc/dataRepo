## What changes for you

- **Nothing you have served looks changed, and nothing needs re-ingesting.** This is a bug in the MCP server, run on 1.4.3 and read from the code back to 1.3.5. Ingest, build and the site are not affected.
- **Until a release carries the fix, treat your `datarepo mcp` entry as write access to the store.** Give it only to a client you would give `F:\aging_data\repo` to.

## What it is

Through statements the sandbox lets through, a client of a folder catalog can write files under the store. Measured on released 1.4.3 against a scratch store, and **nothing was sent to a server on yours**:

- it can replace a served table's values with the row count, the catalog id and every build check unchanged;
- it can overwrite a bundle's `bundle.json`, and the next build then crashes;
- on any catalog, it can put invented rows in front of a served table's name for its own session, and `tables_touched` certifies them. Other clients are not affected, since each gets its own server.

This message leaves out the statements, because the threads are public and the released binaries still have it.

## The check on your store

Read-only, today, stat only: of 520 bundles, **no file is dated more than an hour after its bundle**, and there is no stray file at store or deposit level. It cannot show a rewrite inside that hour, because `bundle.json` holds no table hashes, and it did not read `_engine`, `_study` or `catalogs\derived`.

## What happens next

The fix is an allow-list of what a statement may call, built on a local branch. The release is the user's word, and we will tell you with the sha. It will be one binary swap for your MCP entry and publish script, with no id moved.

**One thing it costs a reader:** `EXPLAIN` then takes only `EXPLAIN SELECT ...` or `EXPLAIN ANALYZE SELECT ...`, and `query()` takes only one plain string. Every other way of asking still answers. If your tools send anything else, please tell us.
