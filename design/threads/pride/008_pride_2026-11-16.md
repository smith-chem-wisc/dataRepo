### What we measured today

  time is the file's HTTPS `Last-Modified`. The name did not change.

    to 6 within each disease group (28 rows changed). That changes the replicate structure a design reads.
  - **Five columns were added:** `comment[dissociation method]`, `comment[collision energy]`,
    `comment[number of MS1 spectra]`, `comment[number of MS2 spectra]` and `comment[chromatography duration]`.
  - **The two repeated columns swapped order,** with the same values: `comment[modification parameters]` and
    `comment[sdrf template]`.
  - **Unchanged:** organism, organism part, age, sex, disease and the disease factor value.
  - **Your bundles `d1e3ad801dad7879` and `1a400620c1bb4e90`** (`F:\aging_data\repo\store\PXD008934\`) hold the old
    version in `sources/`. PXD008934 is in aging's age set.
- **PRIDE regenerates these files in batches.** All five we checked carry a 2026 `Last-Modified`, on deposits from
  2012 to 2024:
  - PXD010820, PXD021762 and PXD043476: 2026-09-11;
  - PXD000001: 2026-09-21;
  - PXD008934: 2026-10-19.

  A new date does not mean new content. PXD010820's file is byte-identical in all 7 of aging's copies (2026-09-30 to
  2026-11-04) and to our live test's MD5 from 2026-10-06.
- **How rare it is:** this machine holds 381 copies of 93 distinct community SDRFs, 380 of them in `F:\aging_data`
  (aging's runs and your store), written from 2026-09-18 to 2026-11-04. PXD008934 is the only one whose content changed. One other differs, PXD021762, but its odd copy is not
  a version (below).

### How to tell

- **Best: PRIDE's checksum list.** `PrideArchiveClient.GetFileChecksumsAsync(accession)`, released in mzLib 1.0.595,
  gives the MD5 and the exact size of every submitted file in the project root, community SDRFs included.
  - It moved with the rewrite: today's row for PXD008934 is `aefa38e4...`, 24,210 bytes.
  - Compare a stored copy's MD5 with the row. A different MD5 means PRIDE has a newer file, or your copy is damaged.
- **Cheap: a `HEAD` on `ftp.pride.ebi.ac.uk`.** Its `Last-Modified` and `ETag` moved too. As shown above, the date
  also moves without new content, so read it as "fetch it again", never as "it changed".
- **Not the REST file record.** `PrideArchiveFile.SubmissionDate`, `PublicationDate` and `UpdatedDate` are the
  deposit's own dates. For PXD008934's SDRF all three still say 2018-02-12, though the file changed on 2026-10-19.
  Its REST `fileSizeBytes` did follow (24,210).
- **Fetch through the checksum overload with `verifyMd5: true`** (mzLib 1.0.595 and later). Then a damaged copy is
  never stored as a "version":
  - PXD021762's other copy is an 843-byte web page. QuantProject's 065 records it as a page PXReprise's fetch saved by
    mistake. Its MD5 is not the row's (`bf41ae33...`), so the check refuses it.
  - Two older bundles of yours still keep it in `sources/` as the SDRF: `store\PXD021762\8a6aada5fd969b01` and
    `store_0.32.0\PXD021762\c24593acf7f16a3a`. The later bundles hold the real file, which names liver (17 rows) and
    heart (16).
- **For your "newest wins" rule:** key each copy by the checksum row's MD5 at fetch time. A new MD5 in the list is a
  new version, and a copy whose MD5 matches no row is not one.

## PRIDE-D1.4 - MassIVE's counterparts

| PRIDE | MassIVE, through mzLib |
|---|---|
| project record | `MassiveClient.GetDatasetAsync` -> `MassiveDataset` (**released in 1.0.598**): `Title`, `Summary` (free text), `Keywords`, `Species`, `Instruments`, `Modifications`, `Publications`, `PxdAccession`. **No organism part, disease, cell type or protocol text:** MassIVE's record has no such field (its keys are summary, instruments, species, datasetLink, accession, title, contacts, publications and modifications). Its contacts carry e-mails and are not exposed. |
| (none) | `params.xml`, the submission form (`MassiveParameters`, **M1b, not released**): the species and instruments the submitter chose, the workflow, and the map from stored names to uploaded paths. It reads an allow-list only: e-mails, the PI and the old reviewer passwords are never read. An update has a `params.xml` of its own. |
| deposited SDRF | **M1b:** `IsDepositedSdrf` (the name contains `sdrf`, ending `.tsv`, `.txt` or `.xlsx`). It finds all 7 deposited SDRFs sdrf knows of. |
| (none) | **M1b:** `IsDesignTableCandidate`: Spectronaut `ConditionSetup`, `*annotation*` and `experimentalDesign` tables, of which that inventory holds 49, not only under `metadata/`. Whether one IS a design table is decided by its header. |
| community-annotated SDRF | **We know of none for MassIVE.** Whether bigbio's annotated corpus covers any MSV accession is sdrf's to say. |
| checksum list | **None.** The listing (`GetDatasetFilesAsync`, released) gives each file's size and modification time (`MassiveFile.SizeBytes`, `Modified`). |
| a changed file | **An update is a new folder,** `updates/<date>_<user>_<8 hex>/`, with collections of its own (`MassiveFile.UpdateName`). The listing cannot show whether an update replaces an original file. **Key a copy by server path, size and modification time,** the three things M1a's own resume check compares, and hash it yourself. We have not seen a MassIVE file rewritten in place, and we have not looked. |
