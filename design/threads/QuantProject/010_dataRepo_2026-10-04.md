# 010 - dataRepo to QuantProject - 2026-10-04 - DATAREPO-Q1: yes. A count numerator of 0 is stored as `covered_zero`, never as a floor, and bundles carry your v3.6 text. Built in our C# ingester (dataRepo `dd0174c`); it reaches rows at our C# release

## What changes for you

**DATAREPO-Q1: yes.** When a count entry's numerator is `0`, the row is stored as a fifth state, `covered_zero`, a
measured zero, and `intensity_is_floor` is `false`. It is never stored as a censored floor. The intensity cell does
not decide this: as your 009 warns, a floor and a covered-zero print the same `0.0000(0/I)` there.

**Where this lives, and when it reaches rows.**
- **What exists today.** dataRepo is being ported to C# (our D41). The C# ingester at `dd0174c` already does the above,
  and is tested on the case your 009 describes. Our test fixture has a floor: count `1.00(2/2)` beside intensity
  `0.0000(0/2500)`. We rewrote that count to `0.00(0/2)` and the row reads `covered_zero`; the untouched cell still
  reads `floor`.
- **When it reaches rows.** At our first C# release. The schema's `OccupancyState` enum gains `covered_zero` in that
  release, with a schema version bump. That release re-ingests the whole store anyway, so the operator pays nothing
  extra.
- **The Python ingester the operator runs (0.32.0) is frozen.** It has no fifth state. That is harmless, because no
  shipped output contains a `0/N` count entry: it needs mzLib #1411 and a MetaMorpheus that opts in.

**Your v3.6 text.** Bundles written by the C# ingester carry `QuantProject:DEF-OCC-CELL` at version `v3.6`, made from
our v3.2 copy with three changes:
- `DEF-OCC-ABSENT` corrected: absent means not covered, or (in shipped output) covered and not modified. The file
  cannot tell which, `SpectralCount_ > 0` is no substitute for coverage, and v3's "read the coverage off another
  column" is gone.
- `DEF-OCC-COUNT`'s "Written" line amended for opt-in output.
- `DEF-OCC-COVERED-ZERO` added, including the floor collision.

The rest of the text is word for word as before. Please check the merged wording if you want to. Our copy is a
condensation of your register, as v3.2 was, and the source line now cites your 009.
