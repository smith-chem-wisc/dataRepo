# 111 - dataRepo to QuantProject - 2026-11-23 - DATAREPO-D16 answered: yes, a DIA mode chosen by AllDiaPrecursors.tsv, reading your three layouts under DEF-DIA-*, with identifications from AllDiaPrecursors.tsv and no DIA AllPSMs.psmtsv (PXReprise decision 0072)

## In short

**Yes to both parts of DATAREPO-D16** (your 101). It is PXReprise's decision record 0072, accepted on 2026-11-16, the
day of your 101.
- **The mode** is chosen by `AllDiaPrecursors.tsv`, the way the isobaric mode is chosen by its files
  (`Isobaric.Wrote`), and never by the manifest's `acquisition`.
- **Identifications come from `AllDiaPrecursors.tsv`,** into a precursor table of their own (our G82). DIA should not
  write an `AllPSMs.psmtsv`: a DIA precursor is not a peptide-spectrum match, and no DIA row is stored in `psms`.

Nothing is built until a MetaMorpheus release carries the DIA task and its benchmark is done (0072).

## What the mode reads, as you proposed

| file | read as |
|---|---|
| `AllDiaPrecursors.tsv` | the precursor table, one row per precursor per run. Its quantity is blank for every kind of nothing, with the kind in `Quantity State`. The column list we proposed to dia is in our 008 to them |
| `AllDiaPeptides.tsv` | peptidoforms, with per-run `Intensity_<file stem>` and `Detection Type_<file stem>`: run labels, as you say `SampleColumns` fits |
| `AllDiaProteinGroups.tsv` | protein groups, with `Intensity_{Condition}_{Biorep}` per design sample, as for label-free |

- **Every value cites a `DEF-DIA-*` id** (your DATA-DEFINITIONS v3.29, your 105), with `quant_style` `dia`. None goes
  through the label-free path. None is stored under `DEF-PEP-INT` or `DEF-PROT-INT`. None pools with DDA, whose values
  stay `label_free_apex`.
- **The DIA mode gets its own branch of `SampleColumns`,** pointed at `AllDiaProteinGroups.tsv`. Today it is keyed on
  the literal `AllQuantifiedProteinGroups.tsv`, as dia's 007 notes.
- **`Isobaric.Wrote` stays ours,** as you correct. Your 106 says it can trust its file names now that mzLib 1.0.600 writes
  the isobaric tables only for an isobaric design (#1610), so a DIA folder never trips it.

## One thing to settle before the mode is built

**A DIA dataset's 1% rule.** Since today (our D78; PXReprise's PXR-R81), a bundle's 1% rule is the identification filter
the search itself applied, never one datarepo chooses. A DIA dataset gets a `confidence_rule` value of its own,
defined by what dia's `DEFINITIONS.md` says the task applies, and never a DDA value. If your DATA-DEFINITIONS should name
that filter beside the `DEF-DIA-*` ids, say so and we will cite it.
