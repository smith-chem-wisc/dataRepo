## DATAREPO-D4 / PXReprise PXR-R23: the shape (proposed; schema 0.0.16)

**Measured first, on the ten searches with a curated design** (your 041's nine and PXD011740). With the SDRF each search
used (PXR-R22), **every design sample is exactly one SDRF source name, and every source name is exactly one design
sample.** That holds for all 181 samples, 165 of them of several files. So a pooled value has a sample to belong to.

1. **`assays` gains a second kind.**

   | column | today | 1.4.0 |
   |---|---|---|
   | `assay_kind` | (new) | `run`: one run's channel, as every assay today. `design_sample`: one design sample of several files |
   | `run_id` | required | NULL exactly when `assay_kind = design_sample`. A pooled sample has no single run, so a true value does not exist |
   | `sample_id` | required | unchanged: the SDRF sample, for both kinds |
   | `design_label` | (new) | MetaMorpheus's column label `{condition}_{biorep}`, verbatim, for every assay placed through a design (pooled or one file); NULL when the table was per run |

   - A pooled assay's id is `<dataset_id>:design:<label>`, e.g. `PXD047289:design:aged_9`. A run's assay keeps
     `<run_id>:<channel>`.
   - A design sample of ONE file stays on its run's assay, as since 1.3.1: its value is the one a per-file table
     would have written.
2. **New table `assay_runs`: the files a pooled assay pools.** One row per (pooled assay, run), with the design's
   `Fraction` and `Techrep` as written. The design itself is already in every bundle as a source (its sha256 is in
   `bundle.json` and in the bundle id), so the values stay tied to the design they hold for (D4).
3. **`quant_values`:** `DEF-PROT-INT` and `DEF-PROT-SPC` rows for protein groups, against the pooled assay. Peptide,
   peptidoform and PSM values stay per file: **no row of theirs ever names a pooled assay.**
4. **`ptm_stoichiometry`:** `CountOccupancy_` and `IntensityOccupancy_` rows against the pooled assay, with
   `denominator_grouping = sample_group`. That value is in the schema today and has never been written.
5. **What the numbers mean is QuantProject's DATA-DEFINITIONS v3.10, cited, never restated:**
   - `DEF-PROT-INT`: per peptide, technical replicates averaged within a fraction, the strongest fraction kept, then
     the median polish;
   - `DEF-PROT-SPC`: summed over the sample's files;
   - `DEF-OCC-*`: the PSMs of all the sample's files pooled.
   The column descriptions say it is not what statistics computes, and that the two must never be compared or pooled.
6. **When a pooled assay is NOT written.** If a design sample's files span several SDRF samples, or one SDRF sample
   holds the files of several design samples, there is no single sample to name. Its values are left out as today,
   with `sample_quant_not_stored` saying which rule failed. They are never split onto runs and never rebuilt from
   per-file columns.

**What a reader sees:**
- `quant_values JOIN assays USING (assay_id)` gives the `sample_id` of every protein-group value, one-file or pooled.
  One query reads per-sample protein values across deposits.
- A query that joins assays to `runs` loses the pooled values (`run_id` NULL), so per-run queries answer as today.
- Counting assays to count runs needs `assay_kind = 'run'`. The MCP descriptions and our derived tables are changed
  to say so, and our build checks it.

**Why not a separate sample-level table:** occupancy already carries `denominator_grouping` for exactly this, and one
join then gives the sample for every value. Two tables would split one definition's values across two places.

On your nine deposits this writes 165 pooled assays.

## DATAREPO-D6 (ask): does this meet D4?

1. **The key.** Is (protein group, pooled assay) right, with the assay naming one SDRF sample and listing its files in
   `assay_runs` with the design's `Fraction` and `Techrep`?
2. **The label.** Is `DEF-PROT-INT` v3.10, cited by every value, plus `assay_kind = design_sample`, enough? Or do
   you want a separate definition id for a sample of several files? Our default is one id: v3.10 says the grain is
   protein group by sample in both cases.
3. **A sample of one file.** It stays on its run's assay. Under your v3.10 its value is the sample's value. Agreed?
4. **Occupancy.** `ptm_stoichiometry` rows against the pooled assay with `denominator_grouping = sample_group`.
   That is your `DEF-OCC-GROUPING` value, written for the first time. Anything else to record?

Our default for each is as written. We build after your answer and PXReprise's.
